# Edge cases and failure modes

A comprehensive audit of non-happy-path behavior across the pipeline: extractor, resolver, pipeline/cache/import_map, CLI/config/NAPI binding, and types/serialization/plugin. Produced by five parallel read-only audits against the codebase as of 2026-08-04, cross-checked against existing test coverage.

**Status update (2026-08-13):** the 43-task remediation plan derived from this audit (see `root-cause-analysis.md` and `docs/archive/2026-08-04-edge-case-remediation-plan.md`) has landed on `main`. Every P0 and P1 finding below is now fixed, including P0-2 (cache staleness — originally deliberately deferred as an architectural tradeoff, revisited and fixed 2026-08-13, see its entry). The extractor's eight component-shape detection gaps (new component-shape recognition, not diagnostic-discipline fixes) are also now closed — six genuinely new-feature fixes, one narrower in scope than originally proposed (see the `Object.assign` entry), and two that turned out to already be resolved by the later-gated `SPEC-EXTRACTOR-001` before this list was updated. This doc is kept as the historical record of what was found; strikethrough + **FIXED** marks resolved items rather than deleting them, so the audit trail stays intact.

**How to read this doc:** findings are grouped by severity tier first (for prioritization), then by subsystem (for context when doing the actual fix). "Tested?" means an existing test exercises exactly this behavior, not just the surrounding happy path.

---

## Severity tiers

- **Crash/hang** — can panic, OOM, or hang the process on realistic or adversarial input.
- **Silent data loss** — violates AGENTS.md non-negotiable #6 ("always emit a Diagnostic when degrading — never fail silently"): output is missing or incomplete with no trace.
- **Silent correctness bug** — output is present but _wrong_, not just missing, with no trace.
- **Contract inconsistency** — behavior diverges from a documented or implied contract (exit codes, schema, precedence rules already established elsewhere in the same codebase).
- **Documented/by-design limitation** — already tracked in `rdt-coverage.md` or `type-checker-integration.md`; listed here only for completeness.

**Resolver — all FIXED:**

- ~~`resolve_named` (type-level resolution) has no cycle detection at all, unlike its chain-level sibling `resolve_props_chain` (`chain.rs`, which tracks a `state.visited` set keyed by `file:type<args>`) — bounded only by `depth > MAX_DEPTH` (20), so a genuinely self-referential type alias resolved at the type level (not via `extends`) recursed 20 frames deep before bailing, instead of being caught immediately with a friendly "circular reference" diagnostic the way the chain-level path already was.~~ **FIXED** (2026-08-13). Naively sharing chain.rs's permanent `visited` set (or mimicking it directly) would have introduced a NEW false-positive class: `resolve_named` is called repeatedly and independently for every unrelated field's type across a whole component, not once per interface, so a permanent set would falsely flag two different, non-cyclic fields that happen to reference the same type (`{ a: Shared; b: Shared }`) as circular — confirmed empirically by temporarily disabling the removal step and watching the guard test fail exactly that way. Fixed instead with a dedicated `ResolveState::named_in_progress` set using proper DFS "currently on this call stack" semantics — inserted on entry to `resolve_named`, removed before it returns — which catches real self-reference while never flagging legitimate repeated reuse. Tests: `self_referential_type_alias_used_directly_as_a_field_type_is_caught_immediately` (confirmed to fail against the pre-fix code, falling through to the generic 20-frame depth-exceeded diagnostic instead), `two_unrelated_fields_sharing_the_same_type_are_not_falsely_flagged_as_a_cycle` (confirmed to fail against a naive permanent-set implementation). `resolver/named.rs:17-53`, `types/global.rs:19-30`

**Pipeline/discovery — all FIXED:**

- ~~`WatchSession::component_cache` is keyed inconsistently between where it's seeded and where it's updated. `initialize()` seeds it from the cold `output.components` map, whose keys already went through Phase 5's same-file duplicate-display-name disambiguation (1st occurrence keys as bare `display_name`; every subsequent occurrence keys as `"<display_name> (<file_path>)"`). `update_file()` inserted re-resolved components keyed by bare `entry.display_name` only, with no disambiguation — two manifestations of the same root cause (`component_cache.insert(entry.display_name.clone(), ...)` was a pure insert, never evicting whatever key(s) that file's components previously occupied): a renamed component left its old-name key behind forever, and — more severely — editing a component that initialize() had disambiguated (because another file already held its bare name) silently overwrote the OTHER file's bare-keyed entry with the edited file's fresh content, while the edited file's own disambiguated key kept its stale pre-edit content.~~ **FIXED** (2026-08-13). `update_file()` now evicts every existing cache entry belonging to the changed file (by whichever key it held) before inserting its freshly-resolved entries, then re-disambiguates against whatever remains — mirroring Phase 5's bare-then-disambiguated rule, checked incrementally instead of via a session-wide counter. ## Documented/by-design limitations (listed for completeness, not new findings)

- Ariakit's `Props<T, O> = O & Omit<ComponentPropsWithoutRef<T>, keyof O>` generic pattern is unmatched at the chain level — `composes` stays empty for 6 of the 10 outlier components tracked in `docs/benchmarks.md`. Matches the already-documented gap.
- Wrapper-call components are detected by shape. `const Button = factory<ButtonFactory>(...)` and `const Item = withContext<HTMLDivElement, ItemProps>(...)` are recognized from the generic call: the props type is read from the type arguments (a factory payload's `props` member, or a declared or `Props`-named reference), and DOM element types are skipped. Measured on source-only mirrors with dependencies not installed (October 2026), Caliper found 332 of the 354 components `react-docgen-typescript` reports with props declared in Mantine core (93%) and 449 of 484 in Chakra v3 (92%), and reported 86% and 85% of those components' declared props. Ant Design (97%), `shadcn/ui` (98%) and `react-spectrum` (99%) were already close. What is still missed: wrapper calls with no type argument, such as `createIconLoader('x')`, `lazy(() => import(...))` and `createIcon({...})` (8 components), which need the return type of the call; and about 64 components that `react-docgen-typescript` reports under a name Caliper does not use, mostly `displayName` assignments and compound members such as `Tabs.List`.
- Mapped types, conditional types, and a couple of `@emotion/styled`-specific call shapes need real type inference OXC deliberately doesn't do — tracked in `docs/type-checker-integration.md` and `rdt-coverage.md`'s known-gaps table.
- Multi-root/monorepo ambient-global (`lib.dom.d.ts` etc.) resolution only inspects `options.src_dirs.first()` — if the first `src_dir` can't resolve `typescript` but a later one could, ambient lookups silently return empty for the whole run. Currently treated as legitimate silent degradation by design; flagged here only because it's untested against an actual multi-root config.
- TOON's format is deliberately lossy relative to canonical JSON (truncated unions, no length cap on descriptions) but this isn't stated in the module's own doc comment — a documentation gap, not a behavior bug.

## Notable non-findings (checked, confirmed sound)

- No `unwrap()`/`expect()`/`panic!()` outside `#[cfg(test)]` anywhere in the extractor, resolver, CLI, or binding crates — non-negotiable #1 holds everywhere it was checked.
- Import re-export cycles are correctly bounded (`MAX_REEXPORT_DEPTH = 8` plus a visited set) with dedicated tests.
- Parallel parse/merge is deterministic: discovery sorts, rayon preserves input order through `collect()`, and the sequential merge phase iterates that same order — diagnostics ordering and dedup winner-selection are reproducible.
- Editor atomic-save patterns (temp file + rename) are explicitly handled in watch mode via `canonicalize_best_effort`.
- Shell injection in config loading is not possible — the config path is passed via `env()`, never interpolated into a shell string, verified across all code paths.

## Watch mode — new, previously-untracked bug (found and fixed 2026-08-12 via Phase 3 spec-drift validation against SPEC-PIPELINE-001)

- **FIXED.** `WatchSession::update_file` bound `new_global` directly to `ArcSwap::rcu(...)`'s return value — but `rcu` returns the value from _before_ the swap (arc-swap's `compare_and_swap` convention: the returned `prev` is the pre-update value), not the value the closure just produced. Every incremental watch update therefore re-resolved affected components against the file's content from _before_ the edit that triggered the update — watch mode was permanently one edit behind. Confirmed against `arc-swap` 1.9.1's own source (`rcu`'s `compare_and_swap`/`prev` naming) before fixing. This was caught by `canon-drift-checker`'s validation of `SPEC-PIPELINE-001`'s AC-015/AC-020/AC-024 against live source and a probe — the spec was correct, the code was wrong, and no existing test caught it (the whole watch-mode test suite only asserted component _identity_, which is invariant under this bug — a component named `Widget` stays named `Widget` regardless of which version of its props resolved). **FIXED**: `rcu`'s return value is now discarded and `new_global` is re-read via `self.global.load_full()` after the swap completes. Test: `update_file_reflects_the_edited_files_new_content_not_its_pre_edit_content` (asserts prop _content_ changes across an edit, not just component presence) — verified to fail cleanly against the pre-fix code before being confirmed against the fix. | `pipeline/watch.rs:171` |

## CLI/config — new, previously-untracked bugs (found and fixed 2026-08-12 via Phase 3 spec-drift validation against SPEC-CLI-001b/d)

- **FIXED.** `WatchSession::snapshot()` always returned `stats: ExtractionStats::default()`, so `watch --out`'s written JSON reported `componentsExtracted: 0` (and every other stats field zeroed) regardless of how many components the session actually held — any consumer reading stats from a watch-mode output file was reading zeros. **FIXED**: `components_extracted` is now computed from the real component count; the other stats fields (files_parsed, dts_cache_hits, duration_ms, tier1/tier3/opaque counts) remain a narrower, still-open gap since they describe a single `extract()` run's bookkeeping that this session doesn't accumulate incrementally. Test: `snapshot_stats_components_extracted_reflects_the_real_component_count`. | `pipeline/watch.rs:139` |
- **FIXED.** A relative `--config` path whose parent directory differs from the process's actual cwd failed with `ERR_MODULE_NOT_FOUND` even though the file existed (e.g. `--config plain/docgen.config.ts` from the repo root). Root cause: `try_load_config` changes the spawned node subprocess's cwd to the config file's parent (so `tsx`/imports resolve relative to the config, not to wherever the CLI was invoked from), but passed the original _relative_ path string through unchanged in `__DOCGEN_CONFIG_PATH` — node then re-resolved that same relative string against the _new_ cwd it had just been given. **FIXED**: the path is now canonicalized before being passed to the subprocess, falling back to the original (relative) path if canonicalization fails so a genuine "file not found" error still names what the user typed. Test: `try_load_config_resolves_a_relative_path_whose_parent_is_not_the_cwd`. | `cli/config.rs:112` |

**Watch mode — component_cache staleness, strengthened (2026-08-12):** Phase 3 validation independently reconfirmed the `component_cache` bare-name-vs-disambiguated-key mismatch already tracked above, and found a second manifestation of the same underlying design gap: `update_file` never _evicts_ a stale entry when a component is renamed between edits (`Card` renamed to `Panel` leaves both `"Card"` and `"Panel"` present in `component_cache`, since the incremental path only ever inserts under the new key and nothing removes the old one). Both manifestations trace to the same root cause — `component_cache.insert(entry.display_name.clone(), ...)` is a pure insert with no corresponding eviction of whatever key(s) that file's components previously occupied. **Still open** — the fix likely needs `update_file` to track and remove a file's previous component keys before inserting its newly-resolved ones, not just a disambiguation-rule fix.

## LSP — new bug found and fixed 2026-08-12 via Phase 3+ spec-drift validation

- **FIXED.** Under `-v`/`-vv` (verbose tracing), `tracing::error!` calls inside `lsp.rs` were written to **stdout** by the default `tracing_subscriber::fmt` writer — corrupting the LSP transport channel, which requires stdout to carry only well-formed `Content-Length`-framed messages. A real editor session with verbose logging enabled would see this ANSI-colored diagnostic text injected mid-stream, desyncing the client. **FIXED**: `init_tracing` now routes all tracing output through `.with_writer(std::io::stderr)` — global, not LSP-specific, since stderr is safe for every command. ## Vite plugin (`packages/vite-plugin`) — first audit, found and fixed 2026-08-13

Never previously covered by this audit — every earlier pass was Rust-only. A read-only research agent mapped the package's architecture and 18 existing (mocked) unit tests, surfacing several real findings; all were investigated and closed in the same pass.

- **FIXED.** `configResolved` built `resolvedSrcDirs` without stripping a trailing slash (relative `srcDirs: ['src/']`, or an already-absolute dir ending in `/`). `isSrcFile`'s `startsWith(`${dir}/`)` check then required a double slash no real file path has — every file under that srcDir was silently excluded from HMR, no error, no log. **FIXED**: trailing slash stripped when resolving. Tests: `still matches files when srcDirs has a trailing slash (relative)`, `... (absolute)`. `packages/vite-plugin/src/index.ts:70-76`
- **FIXED.** `configResolved`'s `napi.createSession()` call was the only NAPI call in the whole plugin with no try/catch, unlike `buildStart`/`coldExtract`. Per the Rust binding's own contract this can legitimately throw (a bad `reactVersion`, malformed option JSON reaching the NAPI boundary) — previously surfaced as a raw, unprefixed native error with no discoverable context. **FIXED**: wrapped, logged with the same `[caliper-docgen]` prefix as every other catch block, then rethrown (sessionId is foundational to every other hook, so swallowing it would just break everything downstream more confusingly). Test: `logs and rethrows when createSession throws`. `packages/vite-plugin/src/index.ts:73-79`
- **FIXED — real bug, not just a coverage gap.** `buildEnd` unconditionally called `napi.closeSession(sessionId)`. Per Rollup's own plugin hook contract (confirmed against the official docs), `buildEnd` fires once _per rebuild_ in `vite build --watch`, not once when the watch process actually shuts down (`closeWatcher` is the correct hook for that). Closing the session on the first rebuild's `buildEnd` would make every subsequent rebuild's `buildStart` auto-vivify a brand new session (the Rust binding's `initializeSession`/`extractFileIncremental` construct one for any unrecognized/closed session id — confirmed via `crates/binding/src/lib.rs`'s `SESSIONS.get`/insert pattern and its own `close_session_on_an_unrecognized_or_already_closed_id_returns_normally` test) — silently losing all incremental-cache benefit on every rebuild after the first. Not a crash (the auto-vivify makes it safe), but a real performance regression directly undermining the tool's core value proposition specifically in watched builds. **FIXED**: `buildEnd` now no-ops during a detected watch build (`command === 'build' && Boolean(config.build?.watch)`); a new `closeWatcher` hook handles the real once-per-process cleanup. Tests: `does not close the session on buildEnd while watching`, `closes the session via closeWatcher when the watch process shuts down`, `still closes the session for a normal (non-watch) vite build`. `packages/vite-plugin/src/index.ts`
- **FIXED (coverage gap, regression-prone).** `configureServer`'s returned teardown function — the exact fix for a real dev-server session leak (commit `49b12c6`) — was never actually invoked by any test; a regression reintroducing the leak would have gone uncaught. Test: `returns a teardown function that closes the NAPI session`.
- **FIXED (coverage gap).** `hotUpdate`'s and `coldExtract`'s malformed-JSON fallback paths (log + send/leave an empty-but-valid result, per their own doc comments) were never exercised. Tests: `sends an empty update and logs when extractFileIncremental returns malformed JSON`, `logs and leaves the virtual module at its placeholder when initializeSession returns malformed JSON`.
- **FIXED (coverage gap, genuine race never exercised).** The `initPromise` queue/replay guard described in the archived plugin spec (a `hotUpdate` call arriving while cold extraction is still in flight must wait for it, not race it) was never actually tested as a race — every prior `hotUpdate` test called the hook directly without `configureServer`, so `initPromise` was always `null`. Test (with a manually-controlled deferred promise, confirmed to fail against the pre-fix code by temporarily removing the `await`): `waits for a still-pending initPromise before calling extractFileIncremental`.
- **FIXED — real bug, found by writing the test.** No sequencing guard existed on `currentOutput.components` mutation in `hotUpdate`. Two overlapping calls for the same file (e.g. a rapid double-save) could have their async NAPI calls resolve out of order, letting an older result silently overwrite a newer one already applied. **FIXED**: a per-file monotonic sequence number, set before the async NAPI call and checked after it resolves — a call that's no longer the latest for its file drops its result instead of applying it. Tests: `drops a stale result when an older hotUpdate call for the same file resolves after a newer one`, `does not let the staleness guard for one file drop a concurrent update for a different file` (confirms the guard is correctly scoped per-file, not global).
- **Confirmed correct-by-design, not a bug.** `.d.ts` files matching `isSrcFile`'s `.ts` suffix check and triggering full extraction is intentional — the core Rust extractor treats declaration files as valid component/interface sources too (`is_tsx = source_type.is_jsx() || is_typescript_definition()`), since a project's own ambient `.d.ts` declarations can affect prop resolution for components declared elsewhere. Previously undocumented; now has a test and an explanatory comment locking in the intent. Test: `treats a .d.ts file inside srcDirs as a valid extraction target`.
- **New: Layer 2 integration test tier built.** The archived plugin spec called for `packages/vite-plugin/tests/integration/` (real `createServer`, real native binding, gated by `NAPI_BINARY_AVAILABLE`, `pool: 'forks'`) — never implemented; only the mocked unit tier existed, and `docs/STATUS.md`'s "fully tested" claim overstated what was actually covered. Built now: 3 tests against the real, locally-built native binary (real cold extraction, real incremental re-extraction via a real file edit, real session teardown on server close), auto-skipping gracefully when no `.node` binary is present (e.g. fresh CI checkouts — the binary is gitignored and not currently built in CI). Building this tier caught that the locally pre-built `.node` binary predated this session's Rust-side fixes entirely (stale artifact, not a live bug) — a `pnpm --filter caliper-docgen-napi build:napi` rebuild resolved it; worth remembering that this tier only reflects reality when the binary is current.
