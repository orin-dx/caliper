# Semantic backend (TypeScript 7)

**Status:** the checker is the default ([ADR 0026](adr/0026-the-checker-is-the-type-authority.md) S8, see "The checker is the default" below): `extract`, `check`, `inspect`, napi sessions and the Storybook addon ask it, and `--no-checker` (`checker: false`) turns it off. It began as an opt-in second resolver ([ADR 0006](adr/0006-semantic-backend-as-second-resolver.md), [ADR 0007](adr/0007-backend-discovers-components-and-compiles-in.md), "Slice 1" below); its answer wins prop by prop (see "The checker's answer wins"). The checker is built in (the `tsrs` crates, see "The checker"); there is no other. Structural extraction is the fallback, and what `--no-checker`, `watch` and the Vite plugin run. Separately, TypeScript 7.1's checker runs as a test-only oracle for structural prop types (`scripts/weekly.py --oracle`, `docs/measurement.md`). **Last verified:** 2026-10-23 for slice 1 against `7.1.0-beta`; 2026-09-27 for the Cost measurements, each naming its nightly; 2026-10-22 for the API table against the `7.1.0-beta` package; 2026-10-23 for the fixture-corpus parity on `7.1.0-beta`.

## Next step

Slice 1 below covers function components by their export. Next, in order: set what `PropType` now carries (index signatures, `readonly`, a ref type's name; optional and rest parameters are done; per-prop `tags` and `parent` are done, see S7a below), class components (generic ones are read at their default: "Generic components" below), and `batchRequests` to cut round trips; watch-mode notifications are done ("Watch" below). The NAPI binding already ships: a session asks a warm checker for the requested component (on by default, ADR 0022). The client's open Lifecycle items in the Gates table still stand.

Some props can't be resolved from the AST alone. The checker backend asks TypeScript's checker instead, using the algorithm react-docgen-typescript (RDT) uses, and merges the answer into the structural result. It runs by default (ADR 0026 S8).

## How it works

```
OXC parse → structural resolver ─────────────────┐
                                                 ├→ merge → ExtractionOutput
tsrs (built in) → semantic resolver (default) ──┘
```

The structural result is complete on its own and returns first. The semantic pass reads each exported component from the checker and replaces the structural props where it finds one.

### Merge rules (proposed)

| Field | Source |
| --- | --- |
| Props present, `type`, `required` | Semantic. A `type` the checker could not read (an `opaque` part) where the structural one is read in full stays structural, marked (see "The checker's answer wins") |
| `parent`, `declarations` | Semantic. `declarations` lists every declaring interface, not just the first |
| `description`, `tags` | Semantic JSDoc, structural if empty |
| `composes` | Semantic: the `@types/react` types the props type is made of |
| `defaultValue` | oxc: the component's code (a destructured parameter's initializer, `defaultProps`), else the checker's `@default` tag; structural where neither has one (S7a2) |
| Components tsc doesn't surface (not exported) | Structural only |
| Structural diagnostics of a resolved component | Dropped where the checker's answer supersedes them (see "Diagnostics a checker answer supersedes") |

### What gets dropped, and where

| Dropped | Where | Status |
| --- | --- | --- |
| `children` without a description | RDT projection only. Canonical keeps it | Done |
| Ambient `.d.ts` components such as `PureComponent` | Merge step | Done |
| `key` | Not emitted, matching the structural path | Closed |
| `ref` | Emitted in `curated` and `full` for `ComponentProps<"div">`-style props and `forwardRef` components, matching the structural path | Closed |
| HTML and DOM attributes in curated and none mode | Semantic adapter, by declaring interface rather than by name | Open |

### Delivery (proposed)

The structural result returns immediately. The semantic result follows: the CLI waits for it, and the NAPI binding exposes a second async call so the Vite plugin can patch when it resolves. Spawn `tsc` at the start of the run so it loads while extraction runs. Each result carries a content hash, and a stale one is dropped.

## Slice 1 (the first opt-in, now the default)

`caliper-docgen extract` (it was `--experimental-semantic-types` until S8; `--no-checker`, or `checker: false` in the config, turns it off). `crates/semantic` asks the checker built into caliper (see "The checker"), builds one program over the files of the components the structural pass found, and asks for each exported function component its call signature's first parameter and that type's properties. The CLI then calls core's `merge_semantic`. Since S8 `check` asks it too, and `inspect` for the one component it shows; `watch` does not, and the NAPI binding asks per component (below).

- **Merge:** props present, `type`, `required`, `parent`, `declarations` and the component's `composes` from the checker, and its description and tags where it has them (see "Declarations, tags and composes"); `defaultValue`, inheritance layers, curated inherited props and `discriminantProp` stay structural. The checker is asked for a prop's description only when the structural pass has none (65% of Mantine's requests otherwise). Props `@types/react` declares are excluded by declaring file. Identical merged props are shared, as in the structural result.
- **Output type:** no new `PropType` variant and no schema change. Primitives, literals, unions (with `boolean` collapsed and `undefined` dropped from optional props), arrays, tuples, inline objects of up to 16 fields and single-signature functions map onto existing variants; `ReactNode`, `ElementType`, `CSSProperties` and `ReactElement` map to their terminals; anything else (named interfaces, enums, generics, overloads, anything past depth 4) is `Named` with the checker's own text. Union members keep the checker's order, which is creation order, not source order.
- **Names:** a symbol's `name` from the checker is its escaped name: a name that starts with two underscores has a third (`__size` arrives as `___size`, TypeScript's `escapeLeadingUnderscores`, so that it cannot collide with internal names such as `__call`). `rpc.rs` removes it when the answer is read, so every name downstream is the one the source writes.
- **Error type:** a name the checker cannot resolve (an import that does not resolve, a name declared nowhere) is typed with its error type, which carries the flags of `any`. Only `Type.intrinsicName` tells it from a written `any`: `"error"` against `"any"`, and the error type has an id per site, so the `any` id says nothing. `rpc.rs` reads `intrinsicName`; `convert.rs` turns an `"error"` type into an `opaque` type with the reason `unresolvableImport` (its `specifier` is the name as the source writes it, since the checker does not say which module was behind it), so the prop has `degradedBy: ["unresolvableImport"]` and a written `any` stays `any` with none. No new diagnostic code.
- **Provenance:** `Info` diagnostics with code `SEMANTIC_BACKEND` whose `affects` lists the output keys: one for the components the checker resolved, one per fallback reason. A first-class per-component field would change the canonical JSON and needs a `SCHEMA_VERSION` bump (`crates/core/src/types/output.rs`).
- **Fallback:** a checker that cannot start or does not answer in time gives the structural result plus one `SEMANTIC_BACKEND` warning, never an error. Per component, the structural result stands for: not exported, class or non-function, overloaded, no props parameter, `any`/`unknown`/union props type, a generic component whose instantiation at its default could not be formed (see "Generic components"), none of the exports the extractor recorded for it found (or found declared in another file), a generic sub-component reached through its parent's property, or a request the checker rejected. Each is listed with its reason.
- **Which export:** the extractor records how the module exports each component (ADR 0027): its export names (`default` included), or for a sub-component attached to an exported one the path through that export (`Menu.Item = Item` beside `export default Menu` is `default.Item`). The checker asks for exactly those, follows an alias to what it aliases, reads an attached sub-component as the property of its parent's type, and checks that the declaration is in the component's file. It never takes the module's `default` unless `default` is a recorded export, and never looks a component up by its display name. Each request carries the component's output key, its answer or fallback carries it back, and the merge (whole-project and session, in time or late) finds the entry by that key alone.
- **Parameter markers:** the checker's parameter symbols carry no optional or rest flag (an optional parameter has the same flags and `checkFlags` as a required one), so `convert.rs` reads them from what the checker prints for the function type: `name?: T` is optional and its `undefined` is dropped from the type, as for an optional prop, `...name: T[]` is the rest parameter; the signature's `flags` (`HasRestParameter`, bit 1) say the last parameter is a rest parameter either way. A parameter whose type is written `T | undefined` stays required. The type is printed with `typeToString` flags `NoTruncation | InTypeAlias` (plus the checker's own defaults): an alias at the top (`type Handler = (value?: string) => void`) is printed as the parameter list it stands for, not as `Handler`, and nothing is cut short. A `this` parameter is printed but is not one of the signature's parameters, and an overload set or a function with properties is printed as an object type whose signatures are read in order. When the printed type still does not give one entry per parameter (a callable interface prints as its name whatever the flags), a parameter is never taken to be required: the type is `opaque` with reason `unsupportedExpression`, so the prop carries `degradedBy`.
- **Not carried:** index signatures, `readonly` and ref names (`PropType` has them since `SCHEMA_VERSION` 4; `convert.rs` doesn't set them), generic parameters of functions.
- **Tests:** `crates/semantic/tests/resolve.rs` runs the backend end to end against the built-in checker (the `markers` fixture project for names and parameters, `tsrs_real.rs` for the error type), and asserts a checker that does not answer in time as the structural output plus one warning. Until trail 369 slice 4 these tests replayed recordings of the Go checker through a fake `tsc` process; with the checker linked in, they ask it directly, and parity with the Go checker is `construct:parity`'s (`apps/oracle/construct-suite/README.md`). The CLI test asserts the default output has no `SEMANTIC_BACKEND` diagnostic.

Measured on `7.1.0-beta`, `extract --json` (best of 2 to 3), flag on against off, plus the base commit's output compared byte for byte (identical apart from `durationMs` on all five corpora, with and without `--load-dependencies`). Peak RSS is the larger of the two processes; on Chakra Caliper is 117 MiB and `tsc` 945 MiB.

### The checker

The checker is built in: the `tsrs` crates (`tsrs_api`, `tsrs_vfs`, pinned `=0.24.0`, TypeScript `3e9236361fa9`, the commit of `typescript@7.1.0-beta`) linked into the CLI and the napi binding. Nothing is installed and no project `typescript` is looked for. It runs by default since S8.

- **Its own threads.** `crates/semantic/src/checker.rs` creates a `tsrs_api::Session` on a thread of its own with a 512 MiB stack, the stack the `tsrs` binary serves on: a query runs on the calling thread, and a type 2,000 deep overflows a default 2 MiB thread, which aborts the process. Requests from any thread reach it over a channel and are answered one at a time; a whole-project `extract` starts a second thread with a channel (a lane) of its own and asks two programs over the same root files, each program's requests down its own lane (`tsrs_api` locks a program's one checker for the length of a request, so two programs are what can be answered at once). Each program has a snapshot of its own (`Rpc::open_programs`): `tsrs_api` registers the handles it hands out in one table per snapshot, behind one lock, which two programs of one snapshot waited on. The second snapshot is derived from the first (`updateSnapshot` with `createPrograms`), so it reads every file from the first's cache, as the first read it, and neither goes to the disk again nor parses a file again: a second `createSnapshot` repeated the file system work of a program build (stat, lstat and read of every file it resolves), which took 25 to 35 ms and raised the run's system CPU time. Every program holds every root file, so either answers a component as one program would; the Storybook session asks one; `Session::handle_request` is the dispatcher the `tsrs` binary serves, so `rpc.rs` sends the methods and JSON of `tsc --api`. A stack overflow aborts and cannot be caught (deep-type tests: 2,000 levels in every run, 10,000 in release).
- **Guards** (trail 369 slice 2). A panic inside the checker comes back as an error for that request (`tsrs_api` catches it, and the thread catches any that escapes), then every lane of the session stops (a whole-project run fails on the first lane's error and answers structurally, with one diagnostic) and the last to leave closes the session: a session a panic unwound through is not asked again, and in a Storybook session the next request starts a fresh one (three crashes and the checker stays down for the session). A panic `tsrs` reports as the client's fault (an unknown `moduleResolution`) is an error like any other and the session is kept. `tsrs` parses on threads of its own with 256 MiB stacks, which a file nested a few hundred thousand levels deep overflows (measured: an object type 200,000 deep parses, 300,000 aborts; generic, tuple, JSX and arrow chains abort between 300,000 and 1,000,000); so every file the checker reads from the disk is measured first, its deepest nesting of `(`, `[` and `{` and, apart, of `<` (5 ms for Chakra's 4.7 MB of declarations, whose deepest is 187), and a request that read one past 20,000 fails with a `SEMANTIC_BACKEND` warning naming it, its components keeping their structural answer. Requests that build snapshots, the ones that read files, run one at a time across the lanes, so a refusal is attributed to the request that met it. A snapshot the refused request made is released before the error goes back, as is one made for a caller that stopped waiting: its id never reaches anyone who could release it. Nesting written without brackets (a chain of arrow types, `a ? b : …`, `1 + 1 + …`) is not measured.
- **Lib files.** The crates embed TypeScript's lib, so a lib declaration's file is `bundled:///libs/lib.dom.d.ts`. The path classifiers read the file name (`lib.*.d.ts`), so it is the lib (`tests/tsrs_real.rs`).
- **Failures.** A checker thread that cannot start, a request past its deadline and a stopped checker give one `SEMANTIC_BACKEND` warning.
- **One checker.** The product has no other route: `--tsc-path` (`tscPath`), which ran a `tsc --api` binary as a process through `crates/tsc-client`, and the version allow-list it was checked against were removed in trail 369 slice 4 (the "Spawn the tsrs binary" alternative of ADR 0026 stays rejected). The Go `typescript@7.1.0-beta` runs only in `apps/oracle`, as the oracle, the construct goldens and `construct:parity`, which compares it with the npm `tsrs` of the same release as the pinned crates (`scripts/check-packaging.mjs` holds the two pins equal).

The client sends `createPrograms[].compilerOptions` (the Node client sends `options`; the server accepts both, and `crates/semantic/tests/resolve.rs` pins the key). Every test that asks a checker (`resolve`, `tsrs_real`, `cases`, `families`, `declared`, `memo`, `exports`, `composes`, `instantiate`, `watch`, `on_demand`) asks the built-in one.

## On demand, per component (on by default)

A long-lived session (the Storybook addon, the lazy `WatchSession`) attaches a warm checker instead of running the whole-project pass above (ADR 0022): a napi session does unless `checker: false`. `caliper-docgen-semantic` keeps one checker warm behind a worker thread, answers from a program rooted at only the requested component's file, and returns its props. The program's snapshot is kept between requests and brought up to date with the files the session says changed ("Watch", below). `WatchSession::component` merges them into the structural answer by name (the checker's type wins, a structural prop the checker did not return stays, and `htmlAttributes` applies once after the merge, as in the structural pass) when they arrive within `semanticWaitMs` (default 150 ms), or within `semanticWaitEmptyMs` (default 2,000 ms, never less than `semanticWaitMs`) when the structural answer lists no props at all (a `ComponentProps<typeof Button>` of a package the structural pass does not model, whose props type it could not expand); otherwise it returns the structural answer plus an `Info` diagnostic, and the checker's late answer serves the next request of the same component while no source file has changed. A kept answer carries what the checker said about the request that made it (a warning that it was not told about an edit, why a component kept its structural result), and every request it serves reports that again, a late answer's included; only an unavailable checker's warning is said once per session. There is one request in flight per component key and content hash of its file: a caller that asks while it is in flight (a story asked while its own prefetch runs, or two stories of one component) waits for that answer, so the checker answers it once. The checker answers interactive requests (`WatchSession::component`, `components`) before background ones (`components_in_background`, which `sessionWarmUp`, the addon's `warmUp` and `fillAfter` use, and which waits for nobody), first come first served within each; an interactive caller that joins a background request raises it, and after 4 interactive answers in a row while background requests wait, the oldest of them goes next. Any source-file change, including a file the component only imports, drops every checker answer, so the next request asks again; an answer still in flight at that moment is neither kept nor joined. The component's structural diagnostics that the checker's props supersede are dropped when they replace the structural ones, except while a structural prop the checker did not return is still opaque: those diagnostics name the component, not the prop, so they stay until nothing they could be about is left. (The whole-project merge drops unreturned structural props, so it has no such case.) Which ones are superseded is in "Diagnostics a checker answer supersedes".

Measured with `crates/semantic/examples/ondemand_bench.rs` (50 random components, TypeScript 7.1.0-beta): the first answer takes 82 to 137 ms (Chakra 703 ms), a component asked for alone 21 to 41 ms (Chakra 534 ms), and 2 to 9 ms when asked for in batches of 8 to 32. Where the structural pass is behind (shadcn) the checker reports 2.3 times the props; where it is not (Mantine, Chakra, Spectrum) it reports the same count. The in-memory cache, the 64-program replacement and the failure modes are in the ADR. (These numbers were measured over the `tsc --api` pipe, before the checker was linked in.)

Hardening of the on-demand checker:

- **Versions:** the checker is the pinned `tsrs` crates; nothing is read from the project.
- **Memory** (trail 369 slice 2): after the first request and every fourth, once the reply is sent, the worker reads what the checker holds and compares it with `OnDemandConfig::max_rss_mib` (768 MiB). The bound is between requests: one request that needs more finishes first. This process's resident memory is the host's as well (Node, Storybook, and Caliper's own answers, which grow by about 5.5 MiB per Chakra component asked), so what is read is the resident part of the one address range `tsrs` carves its arenas from (`mincore`, about 6 ms). Past the bound the checker stops for the session: every later request keeps the structural answer, with a `SEMANTIC_BACKEND` warning that names the bound. It is never replaced, because a fresh session does not lower what this process holds: a closed session gives back part of its arenas (Chakra's 46 MiB fell to 22 to 37), and the fresh one parses every file again. Measured on Chakra (`docs/gate-measurements.md`): 650 edits peak at 377 MiB never replaced against 514 MiB replaced every 64 programs, and the arenas stay at 46 MiB over 2,000 edits and reach 165 MiB over 937 Chakra and MUI components. The range is the process's, so it covers every program and lane of the session; the bound is applied by the Storybook session's warm checker (one lane), and stopping it stops all of it. A whole-project `extract` (two lanes) has no bound: it ends with its process.
- **Converted on the checker's thread:** an answer is converted on the checker's own thread (`Client::run_on_thread`), in a runtime of its own there, so each of its requests (about 3,200 for Chakra's `Button`) is answered in place instead of crossing a channel to the checker and back. The guards are the same: a panic in the session ends it, each request is bounded by `request_timeout` (past it the answer stops waiting and the work's later requests fail, a release excepted), and a panic in the conversion itself leaves the session answering. The first answer for `ChakraButton` went from 145 to 115 ms, and one edit-and-query of `ButtonProps` (`watch`) from 152 to 119 ms at the median (load 6 to 9; these include the reference and prop-key allocation changes).
- **Start and stop:** creating the checker and `warm_up` return at once, and dropping the checker waits at most `shutdown_wait` (5 s) for a request in progress before letting the worker finish alone. The checker's thread finishes a request in progress, then closes its session and exits.
- **Warm-up snapshot:** `warm_up` also builds the snapshot the first request starts from: a program rooted at a file held in the checker's memory (never on disk) that imports each package the nearest `package.json` lists under `dependencies` and `peerDependencies` (`@types` packages are read anyway). Its files are stamped like a request's. The first request brings it up to date with `updateSnapshot`, re-rooted at its own files and with announced edits read again, instead of reading the lib and every dependency from the disk with `createSnapshot`; the warm snapshot is then released. An edit nobody announced is caught as for any kept snapshot. The memory bound is checked after the warm-up too. On `gate-large` (Chakra and MUI) the warm-up takes 63 to 77 ms, its arenas hold 38 MiB, and after the first answer they hold 49 to 50 MiB instead of 40 (peak RSS 20 to 35 MiB higher); `ChakraButton`'s first answer went from 146 to 156 ms to 126 to 149 ms (load 7 to 9).
- **Tests:** `crates/semantic/tests/on_demand.rs` asks the built-in checker.
- **Latency, re-measured** (`ondemand_bench`, 30 components, release build, `7.1.0-beta`): shadcn first answer 84 ms, median 21 ms, p90 37 ms; antd first 93 ms, median 36 ms, p90 40 ms. The memory check does not add to a story's wait.

## The algorithm

Mirrors RDT 2.4.0 (`lib/parser.js`). Method names are from the 7.1 client.

1. `getSymbolOfSourceFile(file)`, then `getExportsOfModule`.
2. For each export, `getTypeOfSymbol`, then `getSignaturesOfType(Call)`. A component has a signature whose first parameter is named `props` or is the only parameter. For a class, use `Construct` signatures and read `props` from the instance type.
3. Props type: `getTypeOfSymbolAtLocation(param, param.valueDeclaration)`. Props: the type's apparent properties, plus each member's when it is a union.
4. Per prop, `type` is `typeToString(getBaseConstraintOfType(t) ?? t)` with default flags, so long types truncate as they do in RDT. `required` means the symbol lacks `Optional` and has no code default.
5. `parent` is the first declaration's parent when that is an interface or type alias. `declarations` is every declaration's parent.
6. `description` and `tags` come from `getDocumentationComment` and `getJsDocTags`.

RDT also emits any exported symbol that has a JSDoc comment but no props. We don't. In the fixture corpus, 23 of the 26 entries only RDT emits are of this kind, such as enum members, type aliases and functions.

### The converter (ADR 0026, slice S2)

A prop's checker type becomes a `PropType` from structured answers only (`crates/semantic/src/convert.rs`): the type flags, a union's members (`getTypesOfType`), a reference's arguments, a tuple type's element flags (`getTargetOfType`), an object's signatures, properties and index signatures (one `batchRequests`), and an alias's symbol and arguments. `typeToString` is used for a name to display, and for two facts the API does not state: which parameter is optional and what a tuple element is labeled (`printed.rs` reads them from the printed type and refuses text that does not read to its end; a fact it cannot read is never replaced by a guess).

- **Named boundary.** An interface or class declared under `node_modules` or in the TypeScript lib (`Date`, `Promise<T>`, `HTMLElement`), and an object type a dependency's alias names, stay `named` with their arguments. A function type is always expanded. The lib's utilities (`Partial`, `Pick`, `Omit`, `Record`) are expanded: their result is the type. A dependency's union of literals is expanded, since its members are the values a control offers. React's `ReactNode`, `ElementType`, `CSSProperties`, `ReactElement` and `JSX.Element` are recognized by where they are declared; `ReactElement` and `JSX.Element` stay `named` (`JSX.Element` named through its namespace, apart from the DOM's `Element`).
- **Caps.** Depth 5, 500 members at the top and 120 below it (a union, an intersection, a tuple's elements), and a budget of 100 properties at the top and 40 below it that counts only the members the project did not declare (inherited from a dependency or the lib, or with no declaration). A cut type is `truncated` with the limit (and, for a width, the total), which `degradedBy` reports. Every descent into the parts of a type (an object, union, intersection, array, tuple or template literal) passes one gate (`Converter::enter`) that checks, before anything is fetched, whether the type encloses itself or is too deep; the width is checked after it, where the type is known. A test has a prop for each cap.
- **Wide object types.** What the project declares is listed whole however wide: an interface of 150 own fields is never cut. Over the budget of members from outside the project, the rest stands as what it is named through, and the project's own members stay beside it. A utility wrapper (`Omit`, `Pick`, `Partial`, `Required`, `Readonly`) is kept as `named` with its arguments when what it applies to has a name of its own: a React DOM attribute type becomes `htmlAttributes` (recognized by the declaring file `/@types/react/` and the interface's name, with the element read from its type argument by the same table the structural path uses, `HTMLAnchorElement` is `a`; an element the table does not know is not guessed), and another dependency or lib type is a `named` layer. The checker keeps no `ComponentPropsWithoutRef`, only the `Omit<..., "ref">` it expands to, which is kept as written. Under the budget the wrapper is expanded (`Pick<ComponentProps<"button">, "disabled" | "type">` has two props). A class or interface of the project that extends such types (`interface BoxProps extends Omit<HTMLAttributes<HTMLDivElement>, "color">`) is an intersection of its own fields and each base type (`getBaseTypes`), a base of the project seen through to its own bases; an instantiation of a generic one, as the type itself or as one base among others, states no bases in terms of its arguments, so the type is cut: its members from outside are `truncated` with their real count beside its own, and the other bases are not named in its place. A type that is not wrapped (`HTMLAttributes<HTMLDivElement>` as a prop) is the `named` it always was.
- **React aliases flattened into a union.** The checker flattens `ReactNode | Fn` into the members of `ReactNode`, so a union that holds all of them (`ReactElement`, `ReactPortal` and an `Iterable` of `ReactNode`, found by declaration, with the primitives) is `reactNode` again beside the rest of its members. `ElementType` below the top of a prop arrives the same way and is wider than the budget: it is recognized (more than 100 of React's own tag names, a fixed table of `JSX.IntrinsicElements`, with `ComponentClass` and `FunctionComponent`) and kept as the terminal instead of cut, and only those tag names go into it: any other string literal the author wrote beside it (`ElementType | "custom-widget"`) stays a member of the union, as does a tag a project adds to `JSX.IntrinsicElements`; narrower, it is listed. `ReactElement` and `JSX.Element` are not collapsed to `reactNode`, which also admits strings, numbers and `null` (ADR 0026, amended 2026-11-13); `ReactChild` is the union of `ReactElement`, `string` and `number`.
- **Recursion** is a `recursive` marker named by the declaration (the alias or interface) with the instantiation's type arguments. Whether a type is one it is inside of is decided by its type handle, which is the instantiation: `Box<string>` inside `Box<Box<string>>` is another type from the one around it and is expanded, while `Tree<string>` inside `Tree<string>` is a back-reference; an alias of an array or tuple of itself (`type Loop = Loop[]`) ends at the first lap. A handle is only compared inside one conversion, never stored in an answer; type handles change with the order of queries, so a test asks last to first and compares bytes. The per-snapshot memo is keyed by the handle, the depth and the set of enclosing handles, so a hit gives what a miss would.
- **Union order.** The checker sorts a union's members by kind and value. The merge puts them back in the order the declaration writes them, read by oxc (see "Defaults and union order" below), and where that does not place every member, in the structural union's order (`types/semantic/order.rs`): a member is found by equality, `boolean` by a boolean literal, a named type by its name without the namespace it was written through (`React.Ref` is `Ref`), and a union the structural pass keeps as string values (`literalUnion`) gives their order. Members the structural union lacks (an `undefined` it dropped, a type it left named) follow the ones it has, in the checker's order. A union neither orders keeps the checker's order, with no marker.
- **Debug stat.** With `RUST_LOG=caliper_docgen_semantic=debug`, each component logs its request count and milliseconds, and the session logs requests by method and memo hits.

### Condition maps

A dependency's condition map is one mapped type instantiated many times over one set of keys: Chakra's `ConditionalValue<V>` is `V | Array<V | null> | { [K in keyof Conditions]?: ConditionalValue<V> }`, and a `Button`'s props hold 538 of them, one per value type, all over `Conditions`' 130 keys. Each is wider than the budget below a prop and is cut, which reads two things of its list of properties: how many there are, and whether the project declared any. Listing them took 31.5 MB and 447 ms one map at a time; the constraint's members take one request of 1.3 ms, which the parts cache keeps.

The converter keeps, per snapshot, the count of a map by `(the handle of its constraint, the symbol that declares it)` (`State::maps` in `crates/semantic/src/convert.rs`), and cuts a later map of the same key without asking for its properties. A map is reused only when all of these hold:

- it is no alias's (a named `Partial<A>` has the type it applies to, which the key does not hold) and has no `as` clause, which would rename the keys;
- the list its count came from had no property the project declares, no signature and no index signature;
- its declaration's keys hold no type parameter, so its properties are declared in the same places whatever it is instantiated with (below, "Who declares the properties");
- the count is over the budget where the later map sits (40 below a prop, 100 at the top). A map that fits is converted from its own properties' symbols and types, which another map's list does not give, so it asks for them.

**When reuse is exact.** A mapped type without an `as` clause has one property per literal key of its constraint, whatever its template, and a handle is one type inside a snapshot, so two maps of one constraint handle have the same keys and as many properties; a mapped type has no signatures, and a counted list with no index signature has a constraint with no `string` or `number`. A cut reads only the count, whether a property is the project's, and the signatures and index signatures (none): what two such maps differ in, each property's type and optionality, it does not read, and the printed text it keeps (`{ c01?: string | undefined; … }`) is asked of each map. The cut is then the same as from the map's own list, and so is everything the conversion above it recorded: the gate, the `asked` set and the enclosing instantiations it compared are unchanged, because no instantiation is looked at between the gate and the cut, and the parts cache is not touched. The entry lives in the snapshot's converter, so a new snapshot starts with none, as the handles it is keyed by do.

**Who declares the properties.** The 7.1 API cannot be asked which type a map is homomorphic over (it has no `getModifiersTypeOfMappedType`), and a key of one constraint handle and one symbol does not say: `type Picked<T, K extends keyof T> = null | { [P in K]?: T[P] }` over the same written-out keys, given a dependency's interface and then the project's, is one key, and the properties of each are declared where its `T`'s are. So a count is kept only for a map whose declaration's constraint holds no type parameter: the declared type's (`getTargetOfType`) keys are the same handle as the instantiation's, which no mapper changed. Chakra's `keyof Conditions` is one; `{ [K in keyof T]?: … }` and `{ [P in K]?: … }` are not, and each of those is listed. The check is one request per map that is listed and counted. The maps fixture (`Generic`) holds it: `Picked<Theirs, Keys>` before `Picked<Ours, Keys>`, the same 45 keys, and the project's fields are all listed.

### The checker's answer wins (ADR 0026, slice S4)

The checker was an explicit opt-in until S8 made it the default (below). When it runs, its answer replaces the structural one prop by prop, at each surface:

- **CLI.** `extract` waits for the checker: every candidate component in one program and one snapshot, as in slice 1. `--semantic-timeout-ms` (default 10,000) bounds the checker's start and each request; past it the run takes the structural result with one `SEMANTIC_BACKEND` warning that says it timed out. It bounds a hang, not the run: on 938 Chakra and MUI wrappers (`~/Projects/caliper-fixtures/gate-large`) the whole answer took 15 to 17 s with the `tsrs` process (its program 71 ms) and takes about 6 s with the built-in checker (S8), well within the default bound.
- **Addon and sessions.** As ADR 0022: the structural answer first, the checker's within `semanticWaitMs` (default 150), a late answer for the next request. The premise that the checker is too slow for a first story still holds with tsrs: Chakra's `Button` (about 1,100 props) takes a median 402 ms through the Rust client (see [gate measurements](gate-measurements.md#first-answer-s4)). Where the structural answer has no props (`Button` among them: the structural pass has props for 140 of the 938 wrappers of `gate-large`), the story waits up to `semanticWaitEmptyMs` (2,000 ms) instead, so its first answer is the checker's. The addon's `prefetchStories` (default 1) pays that wait before a browser asks: when `storybook dev` starts it asks Storybook's docgen service for the opening story's component, which starts the session and the checker and stores the answer where the browser reads it (see [gate measurements](gate-measurements.md#startup-prefetch-trail-332)).
- **A prop the checker could not read.** Where the checker's type of a prop holds an `opaque` part (an import or a name it did not resolve, a conditional type it left open, signatures it could not read) and the structural pass read the same prop's type in full, the prop keeps the structural type and its `degradedBy` also lists the checker's reasons: the checker did not confirm the type, so it is marked rather than silently trusted. One `SEMANTIC_BACKEND` `Info` diagnostic counts those props and names their components. A type the checker only cut at a limit (`truncated`) is still its answer, and so is an opaque checker type where the structural one is opaque too. On the 938 wrappers this applies to 60 props, such as Chakra's `cornerShape`, which the checker answers with its error type, and `storageManager`, whose `StorageManager` it left opaque.
- **Gate.** The construct suite's checker lane holds `checker-expectations.json` against `expectations.json`: no row may rank below the structural path unless it lists an `improvement` reason (`apps/oracle/construct-suite/README.md`, "The checker lane").

### Diagnostics a checker answer supersedes

A diagnostic belongs to the pass that reported it and to the components in its `affects`. Once the checker answers for a component, a structural diagnostic about what that answer replaces no longer describes the component: the prefetch spike (PR 432) found Chakra's `Button` handed to React's docgen with the checker's 1,137 props in hand, because the structural "Cannot find the component 'Button'" warning stayed on the answer and the addon's `fallback: 'degraded'` reads any warning as incomplete props. Each code's decision is `DiagnosticCode::superseded_by_checker` (`crates/core/src/types/diagnostic.rs`, a match with no wildcard arm, so a new code needs one), and one function applies it for both merges, the whole-project one and a session's, in time, late or from the answer cache (`drop_superseded`, `crates/core/src/types/semantic.rs`). It takes the answered component out of the diagnostic's `affects`, and drops the diagnostic once it affects none: a diagnostic several components share stays for those the checker did not answer, and one that affects no component (a file's, the run's) is not touched. It runs before the checker's own diagnostics are added, so it never reads them.

Superseded, so dropped once the checker answers, unless a structural prop the checker did not return still holds a part the structural pass could not read (the diagnostic names the component, not the prop, and may be about it):

- `UNRESOLVABLE_IMPORT`: a component the structural pass could not find (`ComponentProps<typeof Button>` of a factory it does not model), an import or a type name it could not resolve, a builtin name it took as React's. The checker's answer has its own types for those props. It stays when a prop of the merged answer lists `unresolvableImport` in its `degradedBy`: the checker could not resolve a name either, which is the same fault in the project seen by both passes.
- `GENERIC_ARGUMENT_MISMATCH`: an unfilled type parameter left as a bare name in a structural prop type.
- `OPAQUE_TYPE`, `INDEXED_ACCESS_OPAQUE`, `TEMPLATE_LITERAL_OPAQUE`: a structural prop type left opaque or as a pattern. Where the checker could not read the type either, its own marker says so: the prop's `degradedBy`, and the `SEMANTIC_BACKEND` info for props that keep their structural type.
- `MAX_DEPTH_EXCEEDED`, `CIRCULAR_REFERENCE`: where the structural resolver stopped following a prop type.

Not superseded, so they stay:

- `JS_DOC_DEFAULT_MISMATCH`: default values stay structural.
- `DISCRIMINATED_UNION`: `discriminantProp` stays structural.
- `MISSING_TYPE_LIBRARY`: inheritance layers and curated inherited props stay structural.
- `IO_ERROR`, `PARSE_ERROR`, `EXCESSIVE_NESTING`, `SKIPPED_CANDIDATE`: about a file and what the extractor found in it, not a component's props.
- `COMPONENT_KEY_COLLISION`, `DUPLICATE_ENUM_NAME`: about the output's keys.
- `INTERNAL_PANIC`: a defect, whichever pass answers.
- `UNKNOWN`: reported by a consumer, not the structural pass.
- `SEMANTIC_BACKEND`: the checker's own: it is unavailable, it stopped, it has not answered yet, a component kept its structural result (an instantiation that did not form, a component that is not exported), an edit it was not told about, props it could not read.

The addon decides `fallback: 'degraded'` from the warnings and errors left on the answer, which are now the structural ones that still stand and the checker's own.

### Generic components (ADR 0026, slice S5)

A generic component's props parameter has its type parameters open: `function Poly<E extends ElementType = 'div'>(props: PolyProps<E>)` has two props (`as` typed `E`, and its own), where `<Poly />` has every attribute of a `div`. The API has no request that instantiates a signature, so `crates/semantic/src/instantiate.rs` writes the instantiation as source and lets the checker form it:

- **Which instantiation.** The one `<Poly />` renders: the first type parameter's declared default, printed by the checker (`getTypeParametersOfSignature`, `getDefaultFromTypeParameter`, `typeToString`). The checker fills the parameters after it from their own defaults, which may refer to the first. A component whose first type parameter declares no default is unchanged: its props keep the open parameters, since no instantiation is the one a story renders.
- **How.** Once every file is answered, one file, `__caliper_instantiations__.ts` in the project root, declares one line per generic component, `import type { "Poly" as CaliperComponent0 } from "/abs/Poly.tsx"; export type CaliperProbe0 = Parameters<typeof CaliperComponent0<"div">>[0];`, and is added to a second snapshot of the same program through `createSnapshot`'s `fileSystem` layer (`{ "kind": "layer", "files": { path: text } }`), which both tsrs `0.23.0-ts7.1.0-beta` and the Go `7.1.0-beta` read and neither writes to disk. The props are those of `getDeclaredTypeOfSymbol(CaliperProbe0)`, read and converted as any props type is, in that snapshot.
- **Same type, not same name.** A printed default is text read in another module: `type FormData = { id: string }` in the component's module prints as `FormData`, which the probe file, with the default DOM libraries, resolves to the global `FormData` without an error. Each line also declares `CaliperSignature0 = typeof CaliperComponent0` and `CaliperArgument0_0 = <the printed default>`, and a component is read only when `getDeclaredTypeOfSymbol(CaliperArgument0_0)` is, in the probe's own snapshot, the type id of the default `getDefaultFromTypeParameter` gives for that signature (`arguments_keep_their_meaning`, the one place this is enforced). A default that is the same name for another type, or a type written anew (an inline object type), keeps the structural props: `the instantiation Form<FormData> could not be formed: a name in its type arguments means something else where the instantiation is written than in the component's module`.
- **When it cannot form.** The file's errors (`getSemanticDiagnostics`) are matched to components by line, and only errors in the probe file count: the response also holds errors the checker found in other files while forming the instantiations. A component whose line has an error keeps its structural props, and the fallback reason names the instantiation and the checker's message: `the instantiation Configured<Settings> could not be formed: Cannot find name 'Settings'.` (a default the checker prints by a name only the component's module sees). A props type that is a union after instantiation falls back as any union props type does. No props are read from an instantiation that did not form.
- **Cost.** Nothing for a component that is not generic: whether it is comes with the signature already fetched. A generic one costs three requests to find its default; a run with any costs one more snapshot (4 ms on the fixture, the first snapshot's parsed files reused), three requests for the file (its module, exports and errors) and its release, and one per component for the instantiation's type, then the props requests the component would cost anyway.
- **Gate.** `Poly<'div'>` has at least 260 props and `'a'` differs: 281 and 289 on both checkers (`crates/semantic/src/instantiate.rs`, `crates/semantic/tests/instantiate.rs`, against tsrs in the checker lane and the Go checker in Test / Rust). With the whole-project merge, `@types/react`'s props stay with the inheritance layers as for any component, so the CLI shows the component's own props, `as` as `'div'`.

### Watch (ADR 0026, slice S6)

A warm checker keeps the snapshot it answered from, and the next request brings it up to date instead of building the program again (`crates/semantic/src/on_demand.rs`):

- **Telling the checker.** Every change a `WatchSession` applies reaches its checker before any request that may read it: `update_file` and `ensure_fresh` pass the files they applied, a rebuild or a cold start passes "everything" (`SemanticProvider::changed`, `SourceChange`), in the same order as the requests, through the checker's queue.
- **Bringing the snapshot up to date.** `updateSnapshot` with `fileNotifications` (`changed` for a file on disk, `deleted` for one that is gone) and `ensurePrograms: true`; a request for another file also passes `reconfigurePrograms` with its root. Both checkers need `ensurePrograms`: without it a synthetic program keeps the old text even of a file it was told about, and with it the response lists the files whose text changed. Files not named are kept as parsed. A snapshot nothing changed is answered from as it is; an old one is released once its successor exists.
- **An edit nobody announced.** Neither checker sees an edit it is not told about (an update without the file in `fileNotifications` answers from the old text, and so does one told about another file), so before an answer the kept snapshot is checked: after each reply the files its program read are listed (`getSourceFileNames`, 1,855 for Chakra's `Button`) and stamped by modification time and length, and before the next answer they are stamped again (about 1.5 ms on four threads). A file that changed and was not announced makes the answer come from a fresh snapshot (`createSnapshot` reads everything from the disk), with a `SEMANTIC_BACKEND` warning that names the file. A file modified within 2 s of the snapshot's read cannot be told from a later edit by its stamp, so it is read again at every update until it settles: never a warning, never stale. A file that cannot be listed or stamped makes the next request build afresh.
- **Not seen.** A file created, without an announcement, where an import failed to resolve: it is not in the program, so it has no stamp. The session announces creations; only a writer that bypasses it is missed. A change to the tsconfig's compiler options still needs a new process, as before.
- **Memory.** Every request counts toward the 64 programs of a process, and the memory check is unchanged; a replaced process takes its snapshot with it. The built-in checker keeps one session and its snapshot for the whole watch session, bounded as under "On demand" above.

### Declarations, tags and composes (ADR 0026, slice S7a)

Where a prop is declared, its tags and the component's `composes` come from the checker's answer, not from the structural prop of the same name (`crates/semantic/src/declared.rs`, `Converter::composes`), so they no longer depend on the resolver S7 removes.

- **What the protocol states** (tsrs `0.23.0-ts7.1.0-beta` and the Go `7.1.0-beta` answer alike). A property symbol carries its `declarations`, each a handle `<node index>.<kind>.<path>` with the path lower-cased where file names are not case-sensitive, and its `parent` (`{ id, file }`): the interface or type literal it is a member of, absent for a property a mapped type or an intersection made. `getSymbolOfDeclarationForChecker` takes a handle and gives the symbol it declares, with that parent; `getParentOfSymbolForChecker` names the parent and its flags. `getJsDocTags` gives each tag's name and rendered text, `getDocumentationComment` the description. `getSourceFileNames` lists the program's files as they are on disk. `getBaseTypes` gives a class's or interface's bases, `getTypesOfType` an intersection's members.
- **What it does not.** A declaration's offset or line: the handle is a node index into the binary AST `getSourceFile` returns, which the Rust client does not decode, so a checker declaration cannot be joined to oxc's syntax by position. A union's written member order: members come sorted. The declarations of a property mapped from a property that is itself mapped over a generic instantiation (`Pick<ActionButtonProps, 'isDisabled'>` in Spectrum's generic `ActionMenu`): it has none, so it has no `parent`. A default written as a parameter's initializer.
- **`parent`** keeps react-docgen-typescript's meaning, which the structural pass shares: the interface the prop's first declaration is a member of, by name, with the file as the program read it (`getSourceFileNames`, so the case is the disk's). A member of a type literal, inline or behind an alias, has none. A property a mapped type or intersection made is asked about through its declarations, so `Pick<Base, 'p'>` gives `Base`. **`declarations`** is the interface of each declaration that is in one, the first being `parent`.
- **Tags** are keyed as the structural pass keys them (by name, the last repeated tag winning, `@param x` as `param:x`); the merge keeps the structural tags where the checker has none, as for the description. `@types/react`'s props are not asked for tags or descriptions.
- **`composes`** is the `@types/react` types the props type is made of, found by declaring file as React's terminals are (S3): its bases and an intersection's members, through the project's and dependencies' own types and through `Omit`, `Pick`, `Partial`, `Required` and `Readonly` to what they apply to. A type the structural pass could not follow and the checker did is no longer listed. Only names are wanted, so an instantiation of a generic interface (`Props<string>`, which the checker gives no bases of its own) is read through the generic type it instantiates (`getTargetOfType`), whose bases name the same React types; the layers of an over-budget type keep their arguments and still cut at such an instantiation. A list is a decision: `Some([])` says the props type is made of none and replaces the structural `composes`, and `None` (a type on the way whose bases are not known, such as a union or a type parameter) keeps the structural one.
- **Still structural:** `defaultValue` and a union's member order where oxc's syntax does not give them (S7a2, below), inheritance layers and curated inherited props (how `@types/react`'s attributes collapse into a layer), and `discriminantProp` (the checker leaves a union props type to the structural result).
- **Cost.** Per component, one batch for what the snapshot has not been asked yet (each description and tag list kept by its declarations, each declaration's symbol by its handle), one for parents not named yet, and one file listing per snapshot. A description was one request each before, so the 938 Chakra and MUI wrappers of `gate-large` answer in 7.9 to 9.2 s instead of 14.6 to 15.2 s, at a peak RSS 2% higher at most (612 to 615 MB against 601 to 612). Chakra's `Button` first answer is unchanged (median 410 to 416 ms against 417 to 424), and the checker's peak over 60 edits went from 305 to 310 MiB.
- **Measured.** Spectrum (`extract --tsc-path <tsrs>` with the weekly's options, then behind `--experimental-semantic-types`): 3,877 of 4,112 unique props carry `parent` (3,764 of 4,102 before, taken from the structural pass). Of 11,384 props both runs list, 195 gained a `parent`, 29 lost one (the mapped case above) and 6 name the other of two interfaces that declare the prop (the checker's first declaration). `composes` is on 443 of 1,414 components (1,023 before, mostly `@react-types/shared` types the structural pass could not follow). On `gate-large`, 467,019 of the 467,221 props only the checker returns carry `parent`; the other 202 are members of type literals (Chakra's inline `{ axis?: … }`, `recipe`).
- **Gate.** The construct suite compares description, tags, default, required, `parent` and union member order on every row in both lanes (`apps/oracle/construct-suite/README.md`, "Facts").

### Defaults and union order (ADR 0026, slice S7a2)

The checker has no parameter initializer and returns a union's members sorted, so these two facts come from oxc's syntax, read from the files the checker's answer names (`crates/core/src/types/semantic/syntax.rs`), each file once per merge. One function decides each fact in the merge: `default_of` and `declared_order` (`crates/core/src/types/semantic.rs`).

- **Default.** The component's code default for the prop, found by the extractor's own defaults code (`extractor/defaults.rs`, `defaultProps`) on the component's file, matched by display name and exports; else the checker's `@default` or `@defaultValue` tag; else the structural default. The code wins over the tag, as in react-docgen-typescript.
- **Union order.** The union the prop's declaration writes (`crates/core/src/extractor/written.rs`): the member of its `parent` interface in `parent.fileName`, or for a prop with no parent (a type literal), a type literal member of the component's file that is shown to be (part of) its props type: the body of the module-level alias the component's declaration names (or a member of the intersection or union that body is), or a type literal written in the component's declaration outside any body. A type literal elsewhere in the file (an imported props type with a local look-alike) says nothing. A same-file non-generic alias or enum it names is flattened in place, only where it is the declaration in scope: a type parameter, or a type an enclosing namespace, function or block declares, shadows it and the name stays as written. Each alias is flattened once per file, in the module scope, a member stated twice counts once, and a union stating more than 1,024 members through its aliases is not read (a `MAX_DEPTH_EXCEEDED` info diagnostic names the file). A member is matched by what it states (a literal, a keyword, a name it answers to), or by its kind when the written union has one member of that kind (a function, an object literal, an intersection, a template). Where it places every member, its order is used. Where it places some, the structural union's order is used if the structural union placed any member (even when that order is the checker's own), else the placed members come first in written order and the rest follow in the checker's order. Only the top-level union is ordered; a union nested in an object, array or function keeps the structural order where there is one.
- **What oxc alone cannot see.** A union whose members come through an import (`xChannel?: ColorChannel`, `Placement`): following it needs module resolution, which the resolver or the checker has, so the members stay in the checker's order (by kind, then value: not alphabetical, and not marked). A type literal declared in another file than the component's (it has no `parent` to find it by). A `@default` on a prop mapped through `Omit` or `Pick` of an instantiated generic (Spectrum's `Popover` `placement`): the checker gives it no declaration, so no tags. Code defaults the extractor does not read: `defaultProps` assigned in another module or from a variable, spread or computed defaults, and defaults applied inside a hook (`mergeProps`).
- **Switch.** `extract --no-resolver-facts` (hidden, test-only; `ResolverFacts::Off`) makes the merge take neither fact from the structural answer; the construct suite's checker lane runs with it. S7b extends it to the other facts.
- **Measured** (`extract` with the checker, then behind `--experimental-semantic-types`, with the weekly's options, tsrs `0.23.0-ts7.1.0-beta`, against the run before this slice). Before, the structural answer gave the order of 2,736 of Spectrum's 3,194 merged union props and 187 of gate-large's 432,813, and every default: on Spectrum 870 from code, 378 `@default` tags the checker also gives, 15 from the resolver only; on gate-large 499 tags. Now, Spectrum: 27 props gain a code default and none loses one; 11 of 3,686 unions change order, each to the written one (`focusMode?: 'child' | 'cell'`, `slot?: string | null`). With `--no-resolver-facts` 15 defaults (the mapped `@default` case above) and 22 more union orders (imported aliases) differ. gate-large: 834 props gain a default (the checker's `@default` tags of props only the checker returns) and none loses one; 1,452 of 432,690 unions take the written order (`translate?: 'yes' | 'no'`, `css`); with `--no-resolver-facts` no default and 16 more union orders differ (members through an import, such as MUI's `timeout?: TransitionProps['timeout'] | 'auto'`).
- **Cost.** Reading and parsing the files: 0.8 to 1.0 ms of Chakra's `Button` first answer (about 470 ms), whose union props are declared in 83 KB of Chakra's `system.gen.d.ts` and @types/react's 183 KB `index.d.ts`. On gate-large, peak RSS 610 to 616 MB against 608 to 612, and the same CPU time (two runs each).
- **Gate.** Both lanes compare `default` and member order on every row; the checker lane runs with `--no-resolver-facts` and passes every row. Rows `objects/41` to `43` (a destructured default, `defaultProps`, a code default over a different `@default`) and `literals/35` (a type literal's union) cover what a single-file row can; a union through an import needs the cross-file rows of S7b.

### The checker is the default (ADR 0026, slice S8)

The owner's decision (2026-11-12): the checker answers by default on every surface, the whole-project `extract` included, though its default no longer has the structural resolver's speed. One name per concept: `--no-checker` on the command line, `checker: false` in `docgen.config.ts`, the napi options and the Storybook addon. `--experimental-semantic-types`, the config's `experimentalSemanticTypes` and `semanticTypes` are removed: the CLI and the config refuse them as unknown, and the addon refuses `semanticTypes` by name, since left unread `semanticTypes: 'off'` would quietly run the checker.

- **CLI.** `extract` and `check` wait for the checker over every component, `inspect` for the one it shows. `--semantic-timeout-ms` and the test-only `--no-resolver-facts` conflict with `--no-checker`. `watch` stays structural (its help says so).
- **napi and the addon.** A session attaches the warm checker unless `checker: false`, and keeps ADR 0022: the structural answer first, the checker's within `semanticWaitMs` (150 ms), the addon's `prefetchStories` paying the wait of the opening story. `extractAll` stays structural.
- **Vite plugin.** It has no switch and serves the whole output as one module and every transformed file's docs at once, which no checker wait fits, so it creates its session with `checker: false`.
- **Measurement.** The construct suite's structural lane passes `--no-checker`: its expectations are the resolver's. `scripts/weekly.py` (its time, memory, recall and oracle runs), `scripts/agent_eval.py` and `just bench` run the default, the checker, and the weekly's per-corpus budgets are "record on first run" (`docs/measurement.md`, "The budgets"). The checker lane, which held the checker path before, now runs the default, the built-in checker.
- **Cost.** `extract` of `gate-large` (938 Chakra and MUI wrappers): 6.05 s and about 970 MiB by default, 0.10 s and 200 MiB with `--no-checker`; three copies of it (2,814 components) 15.4 s and 1,053 MiB. A lazy session asked for all 938 peaks at 1,058 MiB with the checker against 377 MiB without, once the kept answers share their props (before, about 6.7 MiB per Chakra component, 2.6 GB at 300). The record is [gate measurements](gate-measurements.md#the-checker-is-the-default-s8).
- **Tests.** `crates/cli/tests/commands.rs` holds the default against `--no-checker` on a prop only the checker evaluates (`ReturnType<typeof make>`) for `extract` and `inspect`, and the napi binding's and the addon's tests hold that a session asks the checker unless told not to.

| Topic | Detail |
| --- | --- |
| Where | `microsoft/TypeScript` `main` (`7.1.0-dev`). typescript-go closed on 2026-08-20 |
| Timeline | The plan ([#63703](https://github.com/microsoft/TypeScript/issues/63703)) put the beta on 2026-10-06; npm published `7.1.0-beta` on 2026-10-20. RC 2026-11-10 and stable 2026-11-24 are still planned |
| Get it | `npm i typescript@beta` (`7.1.0-beta`) or `@next` (daily `7.1.0-dev`). 7.0.x (`latest`, `7.0.2`) has no API |
| Launch | `tsc --api [--async] --cwd <dir> --useCaseSensitiveFileNames=<bool>`, plus `--runExternalCode` and `--timing` when asked. With `--async`: JSON-RPC with LSP-style `Content-Length` framing over stdio (`vscode-jsonrpc`), handled concurrently. Without it: msgpack over stdio |
| msgpack caveats | Each message is a 3-element msgpack array: message type (u8), method (bin) and payload (bin). The server answers one request at a time, so a sync client blocks until the reply. Encoded strings are WTF-8: a lone surrogate from a JS string survives, so a Rust client must not decode them as strict UTF-8 |
| Stability | The beta's JS entry points are `typescript/sync`, `/async`, `/proto`, `/ast` and `/ast/*`, `/fs`, `/path` and `/vscode`; the root export is only the version. The `unstable/*` names in ADR 0006 were the nightlies' and are gone. The protocol has no version handshake, so pin the build |
| Positions | UTF-16 code units. OXC offsets are UTF-8 bytes |
| Surface | 177 methods in `7.1.0-beta` (`APIMethodInfo` in `dist/api/proto.generated.d.ts`), up from 157 on 2026-09-19, mostly with TS 6 checker names. Every call in "The algorithm" is present |

**Beta re-probe (2026-10-21, `7.1.0-beta`).** `crates/tsc-client`'s smoke example spawned the beta's `bin/tsc --api`, completed the `initialize` round trip (`caseSensitivity`, `currentDirectory`) and shut down cleanly with exit status 0, so framing and shutdown behave as the fake-tsc harness assumed (both went with the process route in trail 369 slice 4). The beta's `proto.generated.d.ts` still exposes every checker call the algorithm uses: `getTypeAtLocation`, `getTypeOfSymbol`, `getDeclaredTypeOfSymbol`, `getSignaturesOfType`, `getResolvedSignature`, `getReturnTypeOfSignature`, `getBaseTypes` and `getPropertiesOfType`. The fixture-corpus parity run below was re-run on the beta on 2026-10-23 (`apps/oracle` imports `typescript-beta`, `npm:typescript@7.1.0-beta`, since the `unstable/*` entry points are gone). Two beta behaviors to know: the server panics (`interface conversion: interface {} is string, not float64`) when `createProgram` gets string-valued enum options such as `target: 'es2022'`, so pass options from `parseConfigFile`; and `true`/`false` literal types carry neither `value` nor `intrinsicName`, so read them with `typeToString`. Discovery over a whole project ran in the oracle: 33 to 1,531 components per corpus.

**Churn.** About 20 commits touched the protocol definition (`proto.go`) between 2026-08-20 and 2026-09-18. `updateSnapshot`, project IDs and `createProgram` params were reshaped on 09-17 and 09-18. Every call the algorithm uses ran unchanged on the 09-20 and 09-26 nightlies. Re-verify on the beta.

**Freshness.** tsc sees an edit to a dependency only when told:

```js
const s1 = await s0.update({ fileNotifications: { changed: [file] }, ensurePrograms: true })
```

With the notification, the dependent component's props updated (0.5 ms update, 2.8 ms query). An unnotified disk edit stayed stale (2026-09-20). Both incremental paths now notify it (`WatchSession::update_file` and `WatchSession::ensure_fresh`), and an edit neither saw is caught before an answer: see "Watch" above.

The full-corpus run's 257 remaining mismatches, unlike the curated 13, aren't all real algorithm gaps:

- Most are non-component exports the "single-parameter function" heuristic sweeps in — plain string-returning helpers (`antd/buttonHelpers.ts`, `headlessui/render.ts`'s `mergeProps`, `blueprint/blueprintTypes.ts`) whose "props" are `String.prototype`/`Array.prototype` members. - One real RDT bug surfaced: `rdt-compat/svg-icon.tsx` declares two `forwardRef` components (`Icon`, `Box`) in one file; RDT resolves `Box`'s `ref` and DOM-attribute types to `Icon`'s `SVGSVGElement` instead of `Box`'s own `HTMLDivElement`. ## Boundaries

- **`crates/core`** owns the semantic result type, the merge and the diagnostics. It has no I/O, no async and no protocol types. The merge lives here because `OpaqueDetail` and `ParsedProp` internals are `pub(crate)`.
- **Backend crate** (`crates/semantic`, always compiled in and enabled at run time, ADR 0007) links the `tsrs` crates and asks them in process ("The checker"), runs the algorithm, and handles timeouts. Core never depends on it: the CLI runs the backend and calls core's `merge_semantic`.
- **CLI and NAPI** run it by default and turn it off on request. Neither calls JS.
- **Cold path only.** The hook is synchronous and runs on the cold path; `WatchSession::update_file` does not run it.
- **Failure** leaves the structural result and adds a diagnostic. It never fails extraction.
- **Determinism.** Reversing the query order changed no union order across 16 props in 3 files (2026-09-20). Whether canonical output sorts unions is open (below).

## The RDT oracle

`apps/oracle` depends on TypeScript 7.1 directly (for the oracle), but RDT 2.4.0 crashes on import against it (`ts.JsxEmit` is undefined). RDT now resolves its `typescript` peer to `typescript@6.0.3` instead, via the aliased `typescript-beta` dependency (`npm:typescript@7.1.0-beta`, pinned exactly) the oracle imports from — no pnpm override needed, since pnpm overrides don't reliably rewrite a peer dependency's resolution (tried `pnpm-workspace.yaml`'s `overrides: { "react-docgen-typescript>typescript": ... }`; the lockfile recorded it but RDT kept resolving against whatever `typescript` apps/oracle depended on directly).

The removed harness's `compare.ts`/`analyze.ts` (caliper-docgen vs RDT/react-docgen) compared only name, `required`, type and default, and rendered our types themselves in `run-ours.ts` (objects print as `{ ... }`), so their type mismatches mixed resolver and renderer differences. Those limits went with it: `scripts/weekly.py` compares Caliper's own and `@types/react` props with RDT's by name, and the oracle compares prop types structurally against the TS 7.1 checker (`docs/measurement.md`).

## Open decisions

1. **Output type.** Checker types don't fit `PropType` losslessly: `Named` has no file or symbol, and `Tuple` has no optional or rest elements (schema version 5 adds them, with labels and the other kinds ADR 0026's slice S1 lists). Add a variant or map into existing ones. `ExtractionOutput` carries `SCHEMA_VERSION`; a new variant bumps it.
2. **`ref` and `key`.** RDT emits both, and nothing else records forwardRef metadata. Semantic mode must match whatever the structural path does.
3. **Trigger.** Run on every exported component or only on files with degrade diagnostics. Bare generic parameters and TypeScript utility types resolve to `Named` with no diagnostic by design, so the second misses them.
4. **Union order.** Sort in canonical output, or keep source order for structural results.
