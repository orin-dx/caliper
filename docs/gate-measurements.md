# Gate measurements

**Last measured:** 2026-11-09 on `feat/gate-harness` at `f3784be5`, tsrs `0.23.0-ts7.1.0-beta` (the pin), macOS 27.3 on an Apple M5 Max (18 cores, 64 GiB). Two of the gates in [ADR 0026](adr/0026-the-checker-is-the-type-authority.md#gates-before-the-default-flips) need a measurement rather than a test: determinism on a large program and memory past 600 edits; S4 adds a third, the first answer on Chakra (measured on `feat/checker-wins`, see its section). This records how each was made measurable and what it read.

Rerun all three with `just gate-measure` (about 17 minutes). It builds the large project outside the repository (`GATE_FIXTURES`, default `~/Projects/caliper-fixtures/gate-large`, by `scripts/gate_fixtures.mjs`), builds `crates/semantic/examples/gate_harness.rs`, and prints one JSON line per gate. A run that fails its own check exits 1.

## The program

- `scripts/gate_fixtures.mjs` installs `@chakra-ui/react` 3.37.0 and `@mui/material` 9.5.0 (the root `package.json`'s pins) with `pnpm`, and writes one wrapper per exported component, `export function ChakraButton(props: ComponentProps<typeof Button>)`: 1,616 components (1,466 Chakra, 150 MUI). The Chakra and MUI sources themselves were not fetched, so this is not the Chakra corpus of `docs/measurement.md`: it is what an app that wraps both libraries asks the checker.
- Each request to the checker builds a program that loads one library's declarations whole, which is what makes it a large program.
- The harness uses the session a Storybook addon runs: a lazy `WatchSession` with `load_dependencies` on, nothing collapsed, and a warm `OnDemand` that waits up to 120 s, over the pinned tsrs binary the oracle's `tsrs-bin.ts` resolves.

## Memory past 600 edits

- **How.** `OnDemand` now counts its planned process replacements by cause (`recycles()`: `worn` after 64 programs, `bloated` after `max_rss_mib`) and reports the process that answered last (`process_id()`); each replacement is logged at debug level. The harness rewrites one component's file (`ButtonProps & { edit{n}: string }`, which makes the checker load Chakra), calls `update_file`, asks for the component, and reads the process's PID and resident memory from `ps` after every answer, 650 times. It then asks a fresh session over the final files and compares the two answers whole.
- **Result at the shipped bound (768 MiB):** 650 of 650 answers came from the checker and carried that edit's prop (0 stale). The checker ran as 11 processes, 10 replacements, all `worn` and none `bloated`. Peak resident memory was 446 MiB (452 MiB in an earlier run of the same command). The last answer equals the fresh session's.
- **What that shows, and what it does not.** The 64-program limit does the work on this program: a process reached 446 MiB at most, so the 768 MiB bound never fired. The gate asks for the bound to be exercised, so the harness takes `--max-rss-mib`. With 300: 49 `bloated` replacements, 50 processes, no `worn`, peak 331 MiB (a request that grows past the bound finishes first, and the check runs on every fourth request), and the last answer equals the fresh session's again.
- **Verdict: PASS** for what was measured (no leak past 650 edits, replacements keep the answers right, the memory bound works when crossed). Not measured: a program whose single process passes 768 MiB on its own, or a real watch session with the Storybook addon and Node in the loop.

## Determinism across checker counts

- **Not applicable as worded.** tsrs has no checker-count option on the path caliper uses. `tsrs --api --help` lists `-async`, `-callbacks`, `-cwd`, `-pipe`, `-runExternalCode`, `-timing` and `-useCaseSensitiveFileNames`, and `--api --checkers 2` is refused with `flag provided but not defined: -checkers`. The compile mode (`tsrs --checkers 2 -p .`) takes the flag, as `typescript@7.1.0-beta`'s `tsc --help --all` documents, but caliper never runs it: `supervisor.rs` starts `--api --async --cwd` and passes nothing else, and the only thread-count variable among the binary's strings is rayon's `RAYON_NUM_THREADS`.
- **Nearest measurable form.** The output must not depend on how the checker's parallelism is set, on the order components are asked in, or on which process answers. The harness asks a fresh tsrs process for 150 components (every tenth of the 1,616, sorted by key) with `RAYON_NUM_THREADS` set to 1, 2 and 4, three runs each, the middle run asking in reverse order, and byte-compares all nine outputs (each component's JSON entry and diagnostics, sorted by key). The variable changes the process: its thread count read 4, 5 and 7 at 1, 2 and 4. It does not change a checker count, which nothing here sets.
- **Result:** all nine outputs are identical, 341,396,960 bytes each. 148 of the 150 components were answered by the checker in every run; `MuiPopoverRoot` and `MuiSliderMark` kept their structural answer in every run (why the checker declined them was not investigated). So the checker's answers are identical across thread counts, runs, process restarts and query order.
- **Verdict: NOT MEASURABLE as worded; PASS in the nearest form.** The ADR's wording should read "output is deterministic across repeated runs, thread counts, restarts and query order on a large program" until tsrs exposes a count on `--api`. The compile-mode flag was not tried against a program, since its output is not what caliper reads.

## First answer (S4)

- **The gate.** S4: "Chakra first answer at most 150 ms through the Rust client", the addon's default `semanticWaitMs`, which decides whether a first story shows the checker's props or the structural ones.
- **How.** `gate_harness first-answer` (the third gate `just gate-measure` runs) opens, `--runs` times (default 5), a fresh lazy session configured as the addon configures it (dependencies loaded, nothing collapsed, the default `htmlAttributes`), starts the checker in the background as the addon does at creation, waits until that process is up and initialized, then times one `component("ChakraButton")`: the structural pass and the checker's program and conversion for that one component, through the same `OnDemand` the addon uses. It passes when every answer is the checker's and the median is at most `--budget-ms` (150).
- **Result (2026-11-09, `feat/checker-wins`, tsrs `0.23.0-ts7.1.0-beta`, 9 runs, a shared machine at load 13):** every answer was the checker's; median **562 ms** (557 to 575), of which the structural answer is 5 ms and the process start, already done before the request, 5 ms. **FAIL.**
- **Where the time goes.** One answer is about 4,400 requests to tsrs, one at a time: the props of `ButtonProps` are mostly Chakra's style props, each a distinct instantiated union (1,800 `getTypesOfType`, 1,250 `getTypeArguments`, 600 `typeToString`, 560 `batchRequests`, and 43 ms for the snapshot). A request takes about 70 µs, round trip included. Three changes were tried and not kept: converting 16 props at once (360 to 390 ms, but it changes which type handle first asks about a symbol, so the replay fixtures no longer match and would need recording again), batching the requests a level of the walk will make (no faster, so the cost is in the answering, not the round trips) and one documentation batch per component (5%). What would meet 150 ms is fewer requests per component, for example expanding a dependency's instantiated aliases on demand; that is converter work beyond S4.
- **Verdict: FAIL**, so ADR 0022's premise stands with tsrs: a story shows the structural props first and the checker's from the next request on.

### Fewer and cheaper requests (2026-11-10, `perf/checker-first-answer`)

- **Profile.** Every request of one answer logged with its time and answer: 5,271 requests (1,829 `getTypesOfType`, 1,254 `getTypeArguments`, 852 `getDocumentationComment`, 593 `typeToString`, 562 batches of an object's members). 679 of them repeated a request already answered: a type the memo converts again at another depth asks for its members or arguments again. The answers weigh 39 MB, and 31.6 MB of that is the property lists of 562 mapped types: each style prop is `ConditionalValue<V>`, whose condition map has 130 properties and is cut as too wide, which takes the list to count. The client parsed every answer three times: into a `Value`, into a `Value` again, then into its type.
- **What changed.** The client keeps an answer's `result` as text and the backend parses it once, into the type it expects (`Client::request_raw`). A type's members and type arguments are kept by type handle for the snapshot, as the checker's text, so a type converted again asks for neither again. One answer is now 4,593 requests. Output is byte-identical: the whole-program checker run on `gate-large` (938 components) gave the same bytes on main and the branch in 10 runs; the construct suite and checker lane pass; the replay fixtures were recorded again against the pinned tsrs, since the request set shrank.
- **Result:** median **402 ms** (395 to 434) against main's 535 ms (522 to 576), 9 interleaved runs each, every answer the checker's. **FAIL.** The whole-program checker run takes 13.1 s against 15.3 s (5 interleaved runs), the addon's configuration without the checker is unchanged, and peak memory did not grow: caliper 441 MiB against 434, tsrs 563 MiB against 576 (medians of 5 interleaved runs, sampled per process).
- **The other gates, re-run.** `just gate-measure` on the branch: memory PASS (650 of 650 answers the checker's, none stale, 11 processes, 10 `worn` replacements, last answer equal to a fresh session's, peak 478 MiB, then 444 in a second run, against main's 449 and 475 on the same day), determinism PASS (nine outputs of 341,419,093 bytes, all identical), first answer 400 ms over 5 runs, FAIL.
- **Floors, measured.** The branch's 4,593 requests of one answer replayed in order against a fresh tsrs, every answer equal to the logged one: one at a time 348 ms; all of them in 32 batches, so with no round trip left, 162 ms. Add the 40 to 45 ms snapshot and the parse, and an answer of this request set costs about 230 ms however it is batched, prefetched or pipelined. Pipelining does not help either: 1,137 `getTypesOfType` sent at once over one connection took 96 ms, against 86 ms one at a time and 33 ms in one batch, and requests that depend on an earlier answer cannot be sent ahead (with `--async`, tsrs answers out of order, so a handle from an earlier request may not be registered yet).
- **Tried and not kept.** Descriptions in batches of 100 (852 requests become 9, 14 ms off) raised the whole-program run's peak memory by about 17 MiB in caliper and 14 MiB in tsrs, and one batch per component by 55 and 40 MiB. Keeping a type's parts for one component's answer instead of the snapshot held a copy of Chakra's style-prop unions for each of the 16 components answered at once (190 MiB more).
- **What would meet 150 ms:** not fetching the 562 property lists, 81% of the bytes and about 93 ms of the zero-round-trip floor. The converter needs only their count and whether the project declares each property, to cut the type at 40 fields, but tsrs 0.23 has no request that answers that without every property's declarations. Without them the floor would be about 120 to 130 ms, with every remaining request batched.
- **Recommendation.** Keep the 150 ms budget, which is what a story can wait, and keep ADR 0022's structural-first answer; change the seam instead of the budget. Either the addon asks for a story's component before the story is opened (the stories index names them when Storybook starts), so the answer is ready by first paint, or tsrs gains a request that counts a type's properties (or lists their names and flags without declarations), which would bring the cost of an answer near the budget. Raising the budget to the measured 400 ms would make every first story wait that long.

## Not covered

- Other platforms: both measurements ran on macOS arm64. The Linux CI run is a separate gate.
- Wall time was not part of the question; a run takes about 0.5 s per edit here.
- The per-edit `ps` sampling reads the answering process after its reply, so a process that peaked inside a request and shrank before the sample is under-read.
