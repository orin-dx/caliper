# Gate measurements

**Last measured:** 2026-11-09 on `feat/gate-harness` at `f3784be5`, tsrs `0.23.0-ts7.1.0-beta` (the pin), macOS 27.3 on an Apple M5 Max (18 cores, 64 GiB). Two of the gates in [ADR 0026](adr/0026-the-checker-is-the-type-authority.md#gates-before-the-default-flips) need a measurement rather than a test: determinism on a large program and memory past 600 edits; S4 adds a third, the first answer on Chakra (measured on `feat/checker-wins`, see its section), and S6 a fourth, edit-and-query on the snapshot the checker keeps (measured on `feat/checker-watch`, see its section). This records how each was made measurable and what it read.

Rerun them with `just gate-measure` (about 20 minutes), which also runs S6's watch gate. It builds the large project outside the repository (`GATE_FIXTURES`, default `~/Projects/caliper-fixtures/gate-large`, by `scripts/gate_fixtures.mjs`), builds `crates/semantic/examples/gate_harness.rs`, and prints one JSON line per gate. A gate that fails its own check exits 1; the recipe runs every gate and then fails if any did.

## The program

- `scripts/gate_fixtures.mjs` installs `@chakra-ui/react` 3.37.0 and `@mui/material` 9.5.0 (the root `package.json`'s pins) with `pnpm`, and writes one wrapper per exported component, `export function ChakraButton(props: ComponentProps<typeof Button>)`: 1,616 components (1,466 Chakra, 150 MUI). The Chakra and MUI sources themselves were not fetched, so this is not the Chakra corpus of `docs/measurement.md`: it is what an app that wraps both libraries asks the checker.
- Each request to the checker builds a program that loads one library's declarations whole, which is what makes it a large program.
- The harness uses the session a Storybook addon runs: a lazy `WatchSession` with `load_dependencies` on, nothing collapsed, and a warm `OnDemand` that waits up to 120 s. The sections up to S6 ran it over the pinned tsrs binary the oracle's `tsrs-bin.ts` resolved; since trail 369 slice 2, `just gate-measure` runs it on the built-in checker (`--tsc built-in`), on mimalloc as the native binding is, and since slice 4 removed the process route that is its only mode.

## Memory past 600 edits

- **How.** `OnDemand` now counts its planned process replacements by cause (`recycles()`: `worn` after 64 programs, `bloated` after `max_rss_mib`) and reports the process that answered last (`process_id()`); each replacement is logged at debug level. The harness rewrites one component's file (`ButtonProps & { edit{n}: string }`, which makes the checker load Chakra), calls `update_file`, asks for the component, and reads the process's PID and resident memory from `ps` after every answer, 650 times. It then asks a fresh session over the final files and compares the two answers whole.
- **Result at the shipped bound (768 MiB):** 650 of 650 answers came from the checker and carried that edit's prop (0 stale). The checker ran as 11 processes, 10 replacements, all `worn` and none `bloated`. Peak resident memory was 446 MiB (452 MiB in an earlier run of the same command). The last answer equals the fresh session's.
- **What that shows, and what it does not.** The 64-program limit does the work on this program: a process reached 446 MiB at most, so the 768 MiB bound never fired. The gate asks for the bound to be exercised, so the harness takes `--max-rss-mib`. With 300: 49 `bloated` replacements, 50 processes, no `worn`, peak 331 MiB (a request that grows past the bound finishes first, and the check runs on every fourth request), and the last answer equals the fresh session's again.
- **Verdict: PASS** for what was measured (no leak past 650 edits, replacements keep the answers right, the memory bound works when crossed). Not measured: a program whose single process passes 768 MiB on its own, or a real watch session with the Storybook addon and Node in the loop.

## Determinism across checker counts

- **Not applicable as worded.** tsrs has no checker-count option on the path caliper uses. `tsrs --api --help` lists `-async`, `-callbacks`, `-cwd`, `-pipe`, `-runExternalCode`, `-timing` and `-useCaseSensitiveFileNames`, and `--api --checkers 2` is refused with `flag provided but not defined: -checkers`. The compile mode (`tsrs --checkers 2 -p .`) takes the flag, as `typescript@7.1.0-beta`'s `tsc --help --all` documents, but caliper never runs it: `supervisor.rs` starts `--api --async --cwd` and passes nothing else, and the only thread-count variable among the binary's strings is rayon's `RAYON_NUM_THREADS`.
- **Nearest measurable form.** The output must not depend on how the checker's parallelism is set, on the order components are asked in, or on which process answers. The harness asks a fresh tsrs process for 150 components (every tenth of the 1,616, sorted by key) with `RAYON_NUM_THREADS` set to 1, 2 and 4, three runs each, the middle run asking in reverse order, and byte-compares all nine outputs (each component's JSON entry and diagnostics, sorted by key). The variable changes the process: its thread count read 4, 5 and 7 at 1, 2 and 4. It does not change a checker count, which nothing here sets.
- **Result:** all nine outputs are identical, 341,396,960 bytes each. 148 of the 150 components were answered by the checker in every run; `MuiPopoverRoot` and `MuiSliderMark` kept their structural answer in every run (why the checker declined them was not investigated). So the checker's answers are identical across thread counts, runs, process restarts and query order.
- **Verdict: NOT MEASURABLE as worded; PASS in the nearest form.** The ADR's wording should read "output is deterministic across repeated runs, thread counts, restarts and query order on a large program" until tsrs exposes a count on `--api`. The compile-mode flag was not tried against a program, since its output is not what caliper reads.

## First answer (S4)

- **The gate.** S4: "Chakra first answer at most 150 ms through the Rust client", the addon's default `semanticWaitMs`, which decides whether a first story shows the checker's props or the structural ones.
- **How.** `gate_harness first-answer` (the third gate `just gate-measure` runs) opens, `--runs` times (default 5), a fresh lazy session configured as the addon configures it (dependencies loaded, nothing collapsed, the default `htmlAttributes`), starts the checker in the background as the addon does at creation, waits until that process is up and initialized, then times one `component("ChakraButton")`: the structural pass and the checker's program and conversion for that one component, through the same `OnDemand` the addon uses. It passes when every answer is the checker's and the median is at most `--budget-ms` (150).
- **Result (2026-11-09, `feat/checker-wins`, tsrs `0.23.0-ts7.1.0-beta`, 9 runs, a shared machine at load 13):** every answer was the checker's; median **562 ms** (557 to 575), of which the structural answer is 5 ms and the process start, already done before the request, 5 ms. **FAIL.**
- **Where the time goes.** One answer is about 4,400 requests to tsrs, one at a time: the props of `ButtonProps` are mostly Chakra's style props, each a distinct instantiated union (1,800 `getTypesOfType`, 1,250 `getTypeArguments`, 600 `typeToString`, 560 `batchRequests`, and 43 ms for the snapshot). A request takes about 70 µs, round trip included. Three changes were tried and not kept: converting 16 props at once (360 to 390 ms, but it changes which type handle first asks about a symbol, so the replay fixtures no longer match and would need recording again), batching the requests a level of the walk will make (no faster, so the cost is in the answering, not the round trips) and one documentation batch per component (5%). What would meet 150 ms is fewer requests per component, for example expanding a dependency's instantiated aliases on demand; that is converter work beyond S4.
- **Verdict: FAIL**, so ADR 0022's premise stands with tsrs: a story shows the structural props first and the checker's from the next request on.

### Fewer and cheaper requests (2026-11-10, `perf/checker-first-answer`)

- **Profile.** Every request of one answer logged with its time and answer: 5,271 requests (1,829 `getTypesOfType`, 1,254 `getTypeArguments`, 852 `getDocumentationComment`, 593 `typeToString`, 562 batches of an object's members). 679 of them repeated a request already answered: a type the memo converts again at another depth asks for its members or arguments again. The answers weigh 39 MB, and 31.6 MB of that is the property lists of 562 mapped types: each style prop is `ConditionalValue<V>`, whose condition map has 130 properties and is cut as too wide, which takes the list to count. The client parsed every answer three times: into a `Value`, into a `Value` again, then into its type.
- **What changed.** The client keeps an answer's `result` as text and the backend parses it once, into the type it expects (`Client::request_raw`). A type's members and type arguments are kept by type handle for the snapshot, as the checker's text, so a type converted again asks for neither again. One answer is now 4,593 requests. Output is byte-identical: the whole-program checker run on `gate-large` (938 components) gave the same bytes on main and the branch in 10 runs; the construct suite and checker lane pass; the replay fixtures were recorded again against the pinned tsrs, since the request set shrank.
- **Result:** median **402 ms** (395 to 434) against main's 535 ms (522 to 576), 9 interleaved runs each, every answer the checker's. **FAIL.** The whole-program checker run takes 13.1 s against 15.3 s (5 interleaved runs), the addon's configuration without the checker is unchanged, and peak memory did not grow: caliper 441 MiB against 434, tsrs 563 MiB against 576 (medians of 5 interleaved runs, sampled per process).
- **The other gates, re-run.** `just gate-measure` on the branch: memory PASS (650 of 650 answers the checker's, none stale, 11 processes, 10 `worn` replacements, last answer equal to a fresh session's, peak 478 MiB, then 444 in a second run, against main's 449 and 475 on the same day), determinism PASS (nine outputs of 341,419,093 bytes, all identical), first answer 400 ms over 5 runs, FAIL.
- **Floors, measured.** The branch's 4,593 requests of one answer replayed in order against a fresh tsrs, every answer equal to the logged one: one at a time 348 ms; all of them in 32 batches, so with no round trip left, 162 ms. Add the 40 to 45 ms snapshot and the parse, and an answer of this request set costs about 230 ms however it is batched, prefetched or pipelined. Pipelining does not help either: 1,137 `getTypesOfType` sent at once over one connection took 96 ms, against 86 ms one at a time and 33 ms in one batch, and requests that depend on an earlier answer cannot be sent ahead (with `--async`, tsrs answers out of order, so a handle from an earlier request may not be registered yet).
- **Tried and not kept.** Descriptions in batches of 100 (852 requests become 9, 14 ms off) raised the whole-program run's peak memory by about 17 MiB in caliper and 14 MiB in tsrs, and one batch per component by 55 and 40 MiB. Keeping a type's parts for one component's answer instead of the snapshot held a copy of Chakra's style-prop unions for each of the 16 components answered at once (190 MiB more).
- **What would meet 150 ms:** not fetching the 562 property lists, 81% of the bytes and about 93 ms of the zero-round-trip floor. The converter needs only their count and whether the project declares each property, to cut the type at 40 fields, but tsrs 0.23 has no request that answers that without every property's declarations. Without them the floor would be about 120 to 130 ms, with every remaining request batched.
- **Recommendation.** Keep the 150 ms budget, which is what a story can wait, and keep ADR 0022's structural-first answer; change the seam instead of the budget. Either the addon asks for a story's component before the story is opened (the stories index names them when Storybook starts), so the answer is ready by first paint, or tsrs gains a request that counts a type's properties (or lists their names and flags without declarations), which would bring the cost of an answer near the budget. Raising the budget to the measured 400 ms would make every first story wait that long.

### Condition maps are counted once (2026-11-11, `perf/condition-map-memo`)

- **What changed.** The property lists of Chakra's condition maps were the 31.5 MB above: 538 maps of `{ [K in keyof Conditions]?: V }` in `ButtonProps`, one per value type `V`, all over `Conditions`' 130 keys, each fetched to be cut at 40 members. The converter now keeps the count of such a map by its constraint's handle and its symbol, per snapshot, and cuts a later map of that key without asking for its properties, when the list it was counted from had none of the project's, no signature and no index signature, and only where the count is over the budget of the place the later map sits ([Condition maps](type-checker-integration.md#condition-maps)). One request of 1.3 ms (the constraint's members, which the parts cache already holds) replaces them. `getPropertiesOfType` is asked for the first map only, so the 543 batches of one answer fall to 7.
- **Result (2026-11-11, release builds, tsrs `0.23.0-ts7.1.0-beta`, 9 interleaved runs each, a shared machine at load 19 to 28).** Median **277 ms** (273 to 301) against 433 ms (418 to 484) on `main`, every answer the checker's. **FAIL** the 150 ms budget, as before. One answer is 2,975 requests against 3,511 (`getTypesOfType` 1,445, `getTypeArguments` 895 and `typeToString` 573 are the same; the batches are 7 against 543).
- **Output.** The whole-program checker run on `gate-large` (938 components, 8,942,553 bytes of JSON, `--load-dependencies --collapse-inherited-props none`) is byte-identical to `main`'s once the timing `stats` are set aside: two runs of each, compared four ways, and the ten outputs of the five interleaved timing runs of each.
- **Descriptions.** The 848 `getDocumentationComment` requests of the first measurement are gone since S7a: a component asks for what its snapshot has not been asked, in one batch, each description and tag list kept by its declarations. For `ChakraButton` that batch holds 2,548 requests (852 descriptions, 852 tag lists, 844 declarations' symbols), takes 10 to 11 ms of the 210, and covers 852 distinct declarations, so there is nothing more to keep within a snapshot; the components after it share them. No second cache was added.
- **Memory.** One `ChakraButton` answer (7 interleaved runs, sampled every 5 ms): caliper 58 MiB median against 68, tsrs 114 against 135. The whole-program run (13 interleaved runs, sampled every 50 ms): caliper 557 MiB against 551 (543 to 563 against 526 to 564), tsrs 606 against 585 (522 to 622 against 580 to 598), and by `time -l` 607 against 595 over 5 runs. So the whole-program peak is not lower: tsrs is 21 MiB (3.6%) higher in a run whose conversion mostly shares the maps across components already, and the cause was not found (a guess, not measured: with fewer large answers the checker's allocations are collected at other moments).
- **What remains of 277 ms.** The checker answers about 3,000 requests one at a time (1,445 `getTypesOfType`, 895 `getTypeArguments`, 573 `typeToString`), the snapshot, and the conversion. The floor measured above was about 230 ms for 4,593 requests however they are batched, 93 ms of it the property lists; that part is gone, and what is left is what a story still waits for.

## Watch on `snapshot.update` (S6)

- **The gate.** "An unnotified edit fails a test loudly; Chakra edit-and-query p95 at most 25 ms; 300 Chakra edits stay under the threshold." What the slice changed is in [watch](type-checker-integration.md#watch-adr-0026-slice-s6): the warm checker keeps its snapshot and brings it up to date with `updateSnapshot`, and checks the files its program read against their stamps before each answer.
- **The protocol, probed first** (tsrs `0.23.0-ts7.1.0-beta` and the Go `7.1.0-beta`, `~/Projects/caliper-fixtures/s6/probe*.mjs`, a component of `ButtonProps & Extra & { editN }` whose program reads 1,855 files). `updateSnapshot` exists on both. A synthetic program sees nothing without `ensurePrograms: true`: notified or not, a `uri` or a path, `invalidateAll` and a `fileSystem` layer all answered the old text. With it, a notified file is read again and the response lists it under `changedFiles`; an unnotified one stays stale, and so does an unnotified file beside a notified one. A file created where an import failed resolves once announced as `created` or `changed`, and `deleted` removes one. On the Chakra program an update took 16.7 ms median and 26.7 ms p95 over 40 edits (Node client), against 36 to 38 ms for `createSnapshot`.
- **Loud failure.** `crates/semantic/tests/watch.rs` edits a file the component imports without telling the checker: the answer carries one `SEMANTIC_BACKEND` warning naming that file and has the new prop (read from a fresh snapshot). With the comparison disabled the same test fails (no warning, the old prop). It runs on tsrs in the checker lane and on the Go checker in Test / Rust; `crates/core/tests/semantic_hook.rs` holds that `update_file`, `ensure_fresh` and a rebuild each tell the checker.
- **How it was measured.** `gate_harness watch` (the fourth gate of `just gate-measure`): the memory gate's edit loop, `ButtonProps & { edit{n}: string }` rewritten, `update_file`, then the component, timed together, 300 times, with the checker's resident memory and CPU time read after each answer; then the checker's answer alone on its unchanged snapshot, and the edited component and every hundredth other one byte-compared with a fresh session asked in reverse order. `--props own` edits a component with one prop of its own in the same program, so the checker still loads Chakra whole but there is almost nothing to convert. The base is `feat/instantiation-probe` with the same harness (a `createSnapshot` per request).
- **Result, `ButtonProps` (2026-11-10, release builds, a shared machine at load 10 to 29).** 300 of 300 answers the checker's, none stale, none warned, 296 from updated snapshots and 5 created (one per process: 5 `worn` replacements, none `bloated`). Peak RSS 321 to 357 MiB against the base's 440 to 455, under the 768 MiB threshold. Edit-and-query p50 / p95 / p99 in ms: 433 / 565 / 838 alone, then 498 / 1,115 / 1,700 and 515 / 1,572 / 2,422 against the base's 458 / 605 / 882 and 546 / 1,015 / 1,461 interleaved; over 150 edits, 425 / 1,109 and 422 / 782 against 497 / 825 and 466 / 903. The checker's CPU per edit fell from 437 and 737 ms to 56 and 70; caliper's stayed at 222 to 259. The tails moved with the load more than with the branch, and include the first answer of each new process, which builds afresh. **FAIL** (p95 far above 25 ms).
- **Result, own props.** p50 19.8, p95 22.6, p99 47.7 ms (the p99 is the process replacements), checker CPU 23 ms per edit, peak 229 MiB, every answer equal to a fresh session's. The base: 55.2 / 83.3 / 93.9 ms, checker CPU 350 ms, peak 375 MiB. **PASS** in this form.
- **Byte identity.** The edited component and 10 others (sampled every hundredth key) after 300 edits equal a fresh session's asked in reverse order, 20,282,789 bytes, the same count as the base's, in every run.
- **What bounds the `ButtonProps` form.** Converting the answer, not the checker. The same request on the unchanged snapshot takes 330 to 375 ms (`queryOnlyMs`), almost all of it caliper's: about 4,600 requests and their answers to parse per conversion of Chakra's `ButtonProps` (see [first answer](#fewer-and-cheaper-requests-2026-11-10-perfchecker-first-answer)), which an edit makes again because a type's handle and the memo keyed by it belong to one checker. Meeting 25 ms there needs a conversion that survives the edit: a dependency's types cached by declaration across snapshots, which needs the per-component dependency closure ADR 0026 lists as unsolved.
- **The other gates, re-run.** `just gate-measure` on the branch (exit 1, from first answer and watch): memory PASS (650 of 650 answers the checker's, none stale, 11 processes, 10 `worn` replacements, peak 341 MiB against 446 to 478 before, last answer equal to a fresh session's), determinism PASS (nine outputs of 341,419,093 bytes, all identical, as before), first answer 435 ms over 5 runs (409 to 511; the first answer still builds its snapshot with `createSnapshot`, and its files are stamped after the reply), FAIL as before, and watch 520 / 1,161 / 2,727 ms with the checker's CPU at 80 ms per edit, FAIL on the p95 alone.
- **Verdict and recommendation.** The loud-failure and memory parts PASS. Edit-and-query PASSES at p95 22.6 ms where the edit leaves a small props type in a Chakra-sized program, and FAILS for a component of Chakra's `ButtonProps` (p95 565 ms or more), whose floor is its conversion. Keep 25 ms as the budget for the checker's part (the own-props form, which the harness runs with `--props own`), and give the `ButtonProps` form the first answer's budget and seam: its cost is the same conversion.

### Whole-project `extract` against react-docgen-typescript (2026-11-12, `perf/checker-extract-speed`)

- **Same harness.** `scripts/weekly.py`'s own helpers: `program_inputs` (every `.tsx` under `src`, its tsconfig) and `scripts/rdt.mjs` for RDT (`react-docgen-typescript` 2.4.0 from `apps/oracle`, `node --max-old-space-size=8192`), `corpora.run_once` for wall time and peak RSS of each process; Caliper `extract --src <dir> --json --quiet --no-cache`. Three interleaved runs of each, medians, release builds, macOS 27.3 on an Apple M5 Max at load 4 to 6; scratch in `~/Projects/caliper-fixtures/extract-speed`.
- **Before** (`feat/checker-is-default`, `dc27edd7`): `gate-large` (938 components) **6.16 s**, 977 MiB, against RDT's **7.25 s** (7.21 to 7.78), 3,884 MiB: 1.2 times RDT's speed. Chakra alone (787) **5.73 s**, 779 MiB, against RDT's **4.10 s** (3.93 to 4.23), 3,221 MiB: slower than RDT. `--no-checker`: 0.10 s and 0.08 s.
- **Where the 6 s went** (`gate-large`, `samply`, 1 ms samples). 0.17 s structural pass and program; 3.9 s answering, during which caliper's thread was busy 3.3 s (converting 1.1 s, interning each component's copy of each prop 0.8 s, copying converted types out of the memo about 1 s, parsing the checker's JSON 0.6 s, declarations 0.4 s) and waited 0.6 s, while the checker's one thread was busy 2.2 s of it (0.3 s of that writing JSON); then **1.8 s merging** the answer into the output, every component's every prop copied, reordered, hashed and interned again (Chakra's components share about a thousand style props). The run sent 75,000 requests (26,000 `getTypesOfType`, 14,500 `getTypeArguments`, 10,600 `typeToString`, 5,500 `getBaseTypes`); the type memo had 1.09 million hits and 55,000 misses. In process, on Chakra alone, the checker's time is mostly two requests per component: `getPropertiesOfType` (787 requests, 667 ms, 288 MB of JSON out: each props type's thousand properties, every declaration with its full path) and `getTypesOfSymbols` (939, 344 ms, 80 MB out, 42 MB of symbol references in); then `getTypesOfType` (22,600, 223 ms) and nothing else above 60 ms.
- **What changed, each measured after the last** (medians, `gate-large` / Chakra alone):
  - The whole-project merge makes a prop once per checker prop, structural prop, written union and code default (each a shared copy, kept by address while the merge runs; `MergeMemo` in `crates/core/src/types/semantic.rs`): 6.2 s to **4.6 s** on `gate-large`.
  - The converter keeps each prop it answered for the snapshot by what makes it (`PropKey`: the property's name, optionality, declarations and parent, its type's handle, which JSDoc is asked), so a later component converts, copies and interns only the props it does not share: **2.8 s / 2.1 s**.
  - The run converts on four threads (`CONVERTER_THREADS`) instead of one: **2.35 s / 1.75 s**. The checker's thread was then busy 95% of the run.
  - Two programs over the same root files in one snapshot, each on a checker thread of its own (`CHECKER_PROGRAMS`; each program's requests go down one lane, since `tsrs_api` locks a program's one checker per request, and one shared queue first let both threads wait on the same lock), with the files handed to whichever worker is free: **1.73 s / 1.40 s**. Peak RSS grew by about 80 MiB, so the parsed files are shared; each program converts the shared types again.
  - Tried and not kept: three programs, 1.70 s / 1.32 s against two's 1.82 / 1.37 in the same series, for 85 MiB and more CPU, and slower than two at load 30 to 40. Not done: skipping the JSON in process (`tsrs_api` 0.24 has no public typed entry: its `CheckerHost` for a session is private, so `Session::handle_request` with JSON text is the only door); answering from the on-disk cache (ADR 0026's dependency closure is still unsolved, so no invalidation could be shown conservative); skipping requests whose answer looks known (nothing measured asks for less without a new proof).
- **After** (`854da4c6`, same series as the before): `gate-large` **1.82 s** (1.69 to 2.02), 1,077 MiB: **4.0 times** RDT's speed; Chakra alone **1.37 s** (1.32 to 1.38), 870 MiB: **3.0 times** RDT's. With the weekly's settings (`--load-dependencies --collapse-inherited-props none`, cache on) 1.84 s / 1.46 s, 1,160 / 970 MiB. - **Same answer.** The canonical JSON with `stats` set aside is byte-identical to the base's on `gate-large` and Chakra alone, in the default and the weekly settings, over repeated runs. `gate_harness determinism --tsc built-in` passes (nine outputs of 399,060,458 bytes, 1, 2 and 4 threads, each in a fresh process, reversed order included); `memory` passes on both (650 of 650 the checker's, none stale, the last equal to a fresh session's). First answer (`ChakraButton`, 5 runs, two interleaved rounds) 176 and 183 ms against the base's 177 and 176; watch's `ButtonProps` form p50 / p95 165 / 220 ms against the base's 166 / 234 in the same round (the Storybook session asks one program and gains only the prop and merge sharing). `crates/semantic/src/lib.rs` holds three programs to one program's answer, a global augmentation in one file included, and a kept prop to the JSDoc its component asked for; `crates/core/src/types/semantic/tests.rs` holds the merge memo to each component's structural prop.

A `tsrs` request that answers a type's properties with their types, without each declaration's full path, or a public in-process entry that skips the JSON, is what would take the next large step; both are upstream changes.

## Startup prefetch (trail 332)

- **The gate.** In a real Storybook 11 run on Chakra, the first story has the checker's props within 150 ms of the browser's request when the prefetch started at least as long before it as the component's cold cost; a story outside the prefetch is no slower than without it; peak memory at most 30 MB above.
- **How it reaches Storybook.** Storybook 11 starts its docgen worker on the first `extractDocgen` (`createDocgenWorkerClient`: `worker ??= new DocgenWorker`), so nothing in the worker runs earlier. The addon's preset adds an `experimental_devServer` hook, which Storybook applies before the builders start; after Storybook's own hook registers the `core/docgen` service, it reads the story index and calls `getService('core/docgen', { internal: true }).commands.extractDocgen({ id })` (`storybook/internal/core-server`, internal API, Storybook `11.0.0-alpha.9`) for the opening story's component. The command runs the provider chain and writes the answer to the service's state, which the manager receives with its first sync. The manager's Controls panel subscribes once the story is prepared; that subscription's load calls `extractDocgen` again, so the provider is asked a second time and answers from the session, but `isInitialLoading` is false while the stored payload is there, so the panel shows it at once.
- **Harness.** `~/Projects/caliper-fixtures/prefetch`: `storybook dev` (11.0.0-alpha.9, Vite 8, `@storybook/builder-vite` 10.6.2 from the pnpm store with its mock extraction stubbed, since the store has no 11 builder) over 40 stories of `gate-large`'s Chakra wrappers with a `ChakraProvider` decorator, `semanticTypes: 'on-demand'` on the pinned tsrs and `fallback: 'never'`. Playwright opens the root URL as soon as `index.json` answers, as `storybook dev` opens the browser once the index is built. The browser's request and answer times are the manager's websocket frames (`services:command-invoke` for `extractDocgen`, the `core/docgen` state entry); a provider registered after the addon's logs each request in the worker. Shared machine at load 20 to 160; 13 runs with the prefetch (9 of one story, 4 of three) and 9 without, interleaved.
- **Lead time.** The browser asked 1.5 to 6.3 s after the server was spawned (median 2.2 s), 0.8 to 2.3 s after the prefetch started (median 1.2 s); the prefetch starts 45 to 120 ms after the index is built. `ChakraButton` cold through the prefetch took 0.57 to 2.2 s (median 1.0 s): the opening story fits before the browser asks, a second large component does not.
- **Result.** In every run where the prefetch started at least its cold cost before the request (9 runs, and one whose prefetch start was not logged), the checker's 1,137 props were in the browser from 84 ms before to 92 ms after its request (median 10 ms before). Where it had not (3 runs at high load), they arrived 246 to 308 ms after it. Without the prefetch they arrived 0.74 to 2.9 s after the request (median 1.6 s), and once, at load 159, the story got 0 props after its 2 s wait. **PASS.**
- **A story outside the prefetch.** Opened 10 s later: 0.45 to 1.4 s with (median 0.82 s) against 0.64 to 2.1 s without (median 1.0 s). Opened directly at startup, competing with the prefetch: 0.5 to 2.2 s with (median 1.1 s) against 0.82 to 1.7 s without (median 1.35 s). **PASS** in the median; the slowest single value is with the prefetch, at the highest load.
- **Memory.** The Storybook process tree (Node and tsrs), opening the first story: peak 752 to 825 MiB with one story prefetched (median 767) against 720 to 764 without (median 750): **+17 MiB** by median, +22 in each of the two interleaved series; at idle 10 s later within noise. Prefetching 3 stories held about 200 MiB more at idle and made a story opened at startup slower (median 2.2 s), which is why the default is 1.
- **Found on the way.** Storybook hands a preset its own options merged with the addon's; its own `cache` (a file-system cache object) reached the native session as the addon's `cache`, which it refused, so the addon could not start in any real `storybook dev` until the preset dropped a non-boolean `cache`. And with the default `fallback: 'degraded'`, `ChakraButton` is handed to React's docgen even when the checker answers, because the structural warning that `Button` was not found stays on the answer.

## In-process guards (trail 369 slice 2)

The checker is linked into the process since #438, so a fault in it is the host's (Node, Storybook): an abort ends it and memory the checker holds is the host's. Measured 2026-11-11 on `feat/in-process-guards`, release builds, tsrs crates `0.24.0`, macOS 27.3 on an Apple M5 Max, the harness on mimalloc as the native binding is (`--tsc built-in`, on a copy of `gate-large` under `~/Projects/caliper-fixtures/crates-slice-2`).

- **What the memory is.** In process, the host's resident memory cannot stand for the checker's. Asking the 937 components of `gate-large` one at a time, each from the same lazy session, this process grew to 5,365 MiB in process and 4,967 MiB with the checker in a `tsrs` process, sampled every 100 components: 250 to 400 MiB of the difference is the checker, the rest Caliper's own answers, about 5.5 MiB per Chakra component and kept for the session on either route. The checker's own part is read from the one address range `tsrs` carves its arenas from (`tsrs_core::reserve`, `mincore` over it, 6 ms): 42 to 46 MiB for the watch loop below, up to 165 MiB over the 937 components.
- **Replacing the session does not help.** The same 650 Chakra edits (`memory`): replaced every 64 programs as #438 shipped, peak 514 MiB, still climbing at 2,000 edits (533 MiB, 31 replacements); never replaced, peak 327 MiB, flat from edit 200 on, and 389 at 2,000 edits with the arenas at 46 MiB throughout. A closed session gave back part of its arenas (46 MiB fell to 22 to 37 MiB) and the fresh one parsed every file again. Over the 937 components, replacing every 64 changed nothing (5,332 against 5,365 MiB at 900). The reservation `tsrs` aborts on when exhausted (32 GiB) held 95 MiB in chunks throughout 2,000 edits never replaced, and 108 to 110 MiB over 1,000 replaced every 64 (`TSRS_MEM_SPLIT=1`), so a long session does not run it out.
- **The rule.** The built-in checker is never replaced. After its first program and every fourth, its arenas are read; past `max_rss_mib` (768 MiB) it stops for the session and every later request keeps its structural answer with a `SEMANTIC_BACKEND` warning naming the bound (`crates/semantic/src/on_demand.rs`, `Upkeep`). A process is replaced as before. A short-lived helper process for the checker was not built: nothing measured here needs one.
- **Memory past 600 edits** (`gate_harness memory --tsc built-in`): 650 of 650 answers the checker's, none stale, no replacement, peak 343 MiB for the whole process (377 in a second run), arenas 46 MiB, the last answer equal to a fresh session's. **PASS.** The bound exercised (`--max-rss-mib 44`): the checker answered the first 8 edits, was read at 45 MiB, stopped, and the other 642 answers were structural with the bound's warning; the process peaked at 304 MiB and the arenas fell to 22 MiB. **PASS** (the gate requires every answer before the stop to be the checker's and every one after to be structural, with the warning).
- **Determinism** (`gate_harness determinism --tsc built-in`, each variant a fresh copy of the harness with `RAYON_NUM_THREADS` 1, 2 and 4, three runs each, the middle one in reverse): all nine outputs identical, 399,063,798 bytes each; 148 of 150 components the checker's, `MuiPopoverRoot` and `MuiSliderMark` structural in every run, as on the process route. The processes ran 8 to 10, 9 to 13 and 19 threads at 1, 2 and 4. **PASS.**
- **First answer and watch, in passing.** First answer for `ChakraButton`: median 171 ms (169 to 173, 5 runs), against 277 ms over the pipe: **FAIL** the 150 ms budget, closer. Watch on `ButtonProps`: p50 157.7, p95 162.3, p99 168.5 ms, query alone 98.7 ms (565 ms p95 over the pipe): **FAIL** 25 ms. Own props: p50 5.3, p95 6.3 ms, against 22.6: **PASS**.
- **Panics.** A panic inside the checker fails the request it came from; the thread then closes the session and ends, and the next request starts a fresh one, as after a crashed process (three, and the checker stays down). A session a panic unwound through is not asked again, so no later answer reads what it left half-built. `tsrs` itself reports one panic as the client's fault (an unknown `moduleResolution`), and that session is kept. Tests: `crates/semantic/src/checker.rs` (`a_panic_ends_the_session_after_answering_its_request_with_the_error`, with a stand-in session that panics, since the one input known to panic `tsrs` 0.24, an unknown `moduleResolution`, is reported as the client's fault).
- **Stack depth.** `tsrs` parses on its own threads with 256 MiB stacks (`tsrs_compiler::program::worker_pool`), and its checker runs on the 512 MiB `caliper-checker` thread. Nested 50,000 deep, all nine shapes tried parse and print without an abort (an object, generic, `Array`, parenthesis, binary `+`, tuple, arrow and conditional type, and JSX). Past that, a thread of `tsrs`'s own overflows (never `caliper-checker`), which aborts the process: an object type at 300,000 (200,000 parses), a generic at 300,000, a tuple at 500,000 (300,000 parses), JSX at 700,000 (500,000 parses), an arrow chain at 700,000 (500,000 parses), and parentheses and `+` at 1,000,000 (700,000 and 200,000 parse). So the checker is not given a file whose bracket nesting passes 20,000 (`(`, `[` and `{` together, `<` apart): the request that read it fails with a warning naming the file, and its components keep their structural answer. A snapshot that request made (a refused `createSnapshot` or `updateSnapshot`) is released before the error goes back, since its id never reaches the caller; so is one made for a caller that stopped waiting (`checker::tests::a_snapshot_made_by_a_refused_request_is_released_and_the_ones_answered_are_kept`, which fails on `68e9a90e`). The measure costs 5.3 ms for the 4.7 MB of Chakra, Ark, Zag, `@types/react` and `csstype` declarations, whose deepest nesting is 187. Not covered: nesting written without brackets (arrow chains, conditional types, long `+` chains), which overflows only past 500,000. The 10,000-deep test now runs in release in the checker lane.
- **Linux.** CI's `Test / Rust` job (ubuntu) runs the semantic suite on the built-in checker, so the linked crates build and answer on Linux in every PR and on `main` (green at `8212aef8`, #438 included); the measurements above are macOS only.
