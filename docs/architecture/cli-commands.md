# CLI commands

**Source:** `crates/cli/src/main.rs`, `crates/cli/src/config.rs`, `crates/cli/src/output.rs`, `crates/cli/src/commands/mod.rs`, `crates/cli/src/commands/extract.rs`, `crates/cli/src/commands/check.rs`, `crates/cli/src/commands/watch.rs`, `crates/cli/src/commands/inspect.rs`, `crates/cli/src/commands/schema.rs`, `crates/cli/src/commands/completions.rs`, `crates/cli/AGENTS.md`

This is the thin command layer sitting on top of `caliper-docgen-core::pipeline`. It owns nothing about extraction — only argument parsing, calling into the pipeline, formatting output, and deciding the process exit code. Per `crates/cli/AGENTS.md`: "no extraction logic," "no `println!` in command handlers" outside `output.rs`/tracing, and config loading must avoid command injection.

## Command inventory

Six subcommands, dispatched in `main.rs`:

| Command       | Handler                              | Returns       | `--strict`                           |
| ------------- | ------------------------------------ | ------------- | ------------------------------------ |
| `extract`     | `cmd_extract` (`extract.rs`)         | `Result<i32>` | no flag; always `exit_code(false)`   |
| `watch`       | `cmd_watch` (`watch.rs`)             | `Result<i32>` | no flag; always `exit_code(false)`   |
| `check`       | `cmd_check` (`check.rs`)             | `Result<i32>` | yes — `exit_code(args.strict)`       |
| `inspect`     | `cmd_inspect` (`inspect.rs`)         | `Result<i32>` | no flag; always `exit_code(false)`   |
| `schema`      | `cmd_schema` (`schema.rs`)           | `Result<()>`  | n/a — always exit 0                  |
| `completions` | `cmd_completions` (`completions.rs`) | `Result<()>`  | n/a — pure codegen, no pipeline call |

`main()` (`main.rs:175-203`) is the **sole `std::process::exit` call site** in the crate. Every command handler returns a `Result<i32>` (or hardcodes `0` inline for the three that don't call the pipeline), and `main()` maps a non-zero return to `process::exit(exit_code)` after the match. This is stated explicitly in `cmd_extract`'s doc comment (`extract.rs:6-9`) and repeated in `cmd_check`'s (`check.rs:6-8`): keeping the exit decision out of command handlers is what makes it testable — `cmd_extract`/`cmd_check`/`cmd_inspect`/`cmd_watch` all have unit tests that call the handler directly and assert on the returned `i32`, without needing a subprocess harness or capturing a real process exit.

## INVARIANTS

1. **`main()` is the only place that terminates the process for the normal command path.** No command handler may call `std::process::exit` directly for its own success/failure signaling — doing so would make that handler untestable via a plain function call and would bypass whatever cleanup happens between `match` and the final `if exit_code != 0`. (The one deliberate exception is `watch.rs`'s raw-mode keyboard thread, which calls `std::process::exit(0)` on `q`/`ctrl-c` — see Locked Design Decisions.)

2. **No `println!`/`eprintln!` in a command handler for anything the user is meant to read as structured or reusable output — route it through `output.rs`.** `output.rs`'s own module doc states `print_summary` and `print_diagnostics` always write to **stderr**, specifically so `caliper-docgen extract | jq .` never sees human-readable text interleaved with the JSON payload on stdout. Breaking this by adding a stray `println!` in a command handler would silently corrupt every pipe-to-`jq` workflow. (Note: `inspect.rs` and `watch.rs`'s startup banner use raw `println!` directly rather than going through `output.rs` — see Known Gaps; the _stdout-is-payload-only_ half of this invariant still holds for those, since neither writes JSON to stdout by default.)

3. **`docgen.config.ts`'s path is passed to the `node` subprocess via the `__DOCGEN_CONFIG_PATH` environment variable, never interpolated into the script string.** `config.rs:117-126` builds a fixed script body (`"import { pathToFileURL } from 'node:url'; const p = process.env.__DOCGEN_CONFIG_PATH; ..."`) and sets the actual path with `.env("__DOCGEN_CONFIG_PATH", path)`. This is a security-critical invariant, not a style preference: `crates/cli/AGENTS.md` calls it out by name — "The config file path is passed via env var, not embedded in a shell string — command injection risk otherwise." A user-controlled or attacker-controlled path (e.g. a filename containing `` ` `` or `${...}` sequences, or `--config` pointed at a crafted location) must never be able to inject JavaScript into the script `node` evaluates. If a future change reformats this script with `format!("...{path}...")` instead of the env var, that reintroduces the injection.

4. **A `docgen.config.ts` that exists but fails to load is a hard error, not a silent fallback to defaults.** `try_load_config` (`config.rs:112-177`) surfaces node/tsx's real stderr on evaluation failure, and `into_pipeline_options` (`config.rs:33`) rejects unknown fields (`deny_unknown_fields`, which includes options that were removed for doing nothing) and unrecognized `htmlAttributes` strings by name rather than defaulting. This is AGENTS.md non-negotiable #6 ("never fail silently") applied at the config layer: a config the user explicitly wrote getting quietly ignored due to a typo would be a plausible-looking but wrong result forever, and the regression tests for this (`config_schema_rejects_a_typo_d_react_version_instead_of_defaulting`, `try_load_config_surfaces_the_real_syntax_error_not_just_an_exit_status`) are both named after adversarial-review findings where the code used to fail this contract silently.

5. **`ExtractionOutput::exit_code(strict: bool) -> i32` is the single source of truth for the 0/1/2 exit-code mapping, and every command that reports it must call this method rather than re-deriving the check.** The mapping (`core/types/output.rs:42-55`): `Error` present → `2`; `Warning` present and `strict` → `1`; `Warning` present and not `strict` → `0`; `Info`-only or clean → `0`. `extract`, `check`, `watch`, and `inspect` all now call this one method (see Locked Design Decisions — this was a real duplication bug, fixed).

6. **`--json` on `extract` must still run the same `exit_code(false)` check as the human-readable path — it must not return early.** `extract.rs:44-68`: the `if args.json { ... }` branch prints and falls through to the same `Ok(output.exit_code(false))` at the bottom of the function rather than having its own early `return Ok(0)`. The regression test `json_mode_still_returns_the_error_exit_code` (`extract.rs:176-183`) is named directly after the adversarial-review finding this fixed: `--json` used to return before the exit-code check ran, so `extract --json` always exited `0` even on a hard error — "the one signal CI actually depends on," per the test's own comment.

7. **`watch`'s exit code must come from the session's cumulative snapshot, not the current file-change event's own diagnostics.** `watch.rs:142-143` explicitly sources `watch_exit_code` from `session_inner.snapshot()` — the whole tree's current diagnostic state — rather than from just the `update` returned by `update_file(&utf8)` for this one edit. The comment at that call site spells out why: sourcing from the per-event delta would let a clean edit to file A reset the tracked exit code to 0 even though file B, untouched in this event, still has an unresolved error.

8. **`watch`'s output-file writes are atomic (`write_atomic`, `watch.rs:17-39`): temp file in the same directory, then `rename`.** A mid-write failure (disk full, permission revoked) must never leave the `--out` path holding truncated JSON, since some other process (a bundler, a dev-server file watcher) may be reading that path concurrently and can't tell a half-written file from a valid empty one.

9. **`watch --out` holds the current snapshot from startup on.** `start_session`, every change and `r` all go through `publish`, which tracks the exit code and rewrites `--out`. An event that produced no new session revision (a non-source or excluded file) writes nothing, so downstream watchers are not triggered for no change. The watcher also watches the tsconfigs, `package.json` files and lockfiles above the source directories (`watched_paths`); a change to one rebuilds the session through `update_file`. `r` calls `WatchSession::rebuild()` for changes the file watcher cannot see (a package edited in `node_modules`).

10. **The keyboard thread's raw mode keeps output processing on (`OPOST | ONLCR`).** Raw mode is needed to read single keys, but it also stops `\n` from returning the cursor to column 0, which staircases every line printed during the session. `keep_output_processing` restores it; `raw_mode_keeps_newline_translation_for_output` checks it on a real pty.

11. **`inspect` must still surface Error-severity diagnostics found elsewhere in the source tree, even when the specifically-inspected component is clean.** `inspect.rs:82` calls `output.exit_code(false)` unconditionally after a successful component lookup, using the full `output` from `pipeline::extract`, not a filtered view scoped to just `args.component`. The test `inspect_surfaces_error_exit_code_from_diagnostics_elsewhere_in_the_tree` pins this down with a fixture where the inspected component (`Comp.tsx`) is valid but a sibling file (`Bad.tsx`) has a parse error, asserting exit code `2`.

## LOCKED DESIGN DECISIONS

**Exit-code logic lives in `core/types/output.rs`, not the CLI crate, despite `crates/core/AGENTS.md`'s "no terminal/display code in `crates/core`" rule.** This looks like a rule violation at first glance — exit codes are a very CLI-flavored concept. It isn't: `docs/root-cause-analysis.md` cluster 11 documents that this was originally a _doc-comment convention re-typed per command_ (`extract.rs` and `check.rs` each independently implemented the same 0/1/2 check with syntactically different code, and `cmd_watch` used to return `()` with `main.rs` hardcoding exit `0` for that arm, and `cmd_inspect` never touched `output.diagnostics` at all). The fix — `impl ExtractionOutput { pub fn exit_code(&self, strict: bool) -> i32 }` in core — was deliberately scoped as "pure data-in/data-out, same category as the existing `html_element()` helper," which is why it doesn't violate the core/no-terminal-code rule: `exit_code()` computes an `i32` from data, it doesn't print anything or touch a terminal. Do not "fix" this by moving the logic into the CLI crate; that would resurrect the exact duplication cluster 11 documents.

**Only `check` exposes `--strict` as a CLI flag; `extract`, `watch`, and `inspect` always call `exit_code(false)`.** This asymmetry is intentional but only loosely documented. `docs/root-cause-analysis.md` cluster 11 explicitly preserves it ("note `check.rs` additionally supports a `--strict` warnings-escalate-to-1 path that `extract.rs`'s args have no equivalent flag for today; preserve that distinction rather than assuming the two commands' checks are fully identical"), and `docs/edge-cases.md` P3-1 separately flags the consequence: "`watch` always exits 0 regardless of extraction errors — fine for an interactive dev loop, but a footgun if ever run non-interactively (CI, pre-commit)." So the asymmetry is a deliberate, load-bearing design choice for `check` (whose whole purpose per its doc comment is "For CI"), but it is **not** independently justified anywhere for why `extract`/`watch`/`inspect` shouldn't also grow a `--strict` flag — P3-1 marks it as an accepted-but-unresolved gap rather than a closed decision. Treat "should `extract --strict` exist" as an open question, not a settled one, if it comes up again.

**`node`/`tsx` is spawned with `command.current_dir(dir)` set to the _config file's own directory_, not the CLI's invocation `cwd`.** (`config.rs:130-137`.) This matters for two real scenarios the comment names directly: `--config ../other-project/docgen.config.ts` pointing outside the current project, and a project whose `tsx` devDependency isn't hoisted to wherever the caller happened to invoke the CLI from. Resolving `tsx` (and anything the config file itself imports) relative to the config file's directory, via Node's own ancestor-walking package resolution, is what makes both cases work. Don't "simplify" this to always use the CLI's own `cwd`.

**`DocgenConfigSchema` uses `#[serde(deny_unknown_fields)]` and only maps a _deliberate subset_ of `PipelineOptions`.** The struct's own doc comment (`config.rs:5-12`) states this is deliberate: `extraPaths` and `knownTypeOverrides` need complex map/object values not yet supported via config file, and `deny_unknown_fields` means using one of those (or a typo'd key) produces a named error rather than a silently-ignored setting — "same reasoning as this module's existing 'found but unsupported' hard error." Adding a new `PipelineOptions` field without adding it here is a silent-gap risk in the _other_ direction (a config author can't set it at all, with no error telling them so) — but relaxing `deny_unknown_fields` to fix that would reopen the typo-swallowing hole non-negotiable #6 exists to close. The fix is to extend the schema, not loosen the validation.

**`watch`'s keyboard-input thread calls `std::process::exit(0)` directly on `q`/ctrl-c** (`watch.rs:101-104`), which is the one deliberate exception to Invariant 1. It's spawned as a detached `std::thread::spawn` reading raw terminal events in a loop with no owned `JoinHandle` the main thread waits on — there's no `Result<i32>` return path back to `main()` from inside that thread, and disabling raw mode (`crossterm::terminal::disable_raw_mode()`) before exiting is itself part of why the exit happens inline rather than via a channel-and-return.

**`extract --json` intentionally ignores `--out`/`--format`.** `ExtractArgs::json`'s doc comment (`main.rs:103-107`) states this precisely: `--json` is "the canonical schema, compact, always to stdout, ignoring --out/--format (which govern the human/RDT paths below), and suppresses the human-readable summary/diagnostics." This is a deliberate two-mode split (machine-readable canonical vs. human/RDT-formatted), not an oversight where `--json --out foo.json` should have written to the file — it never will, by design.

## The RDT serializer is core code the CLI and the binding share

`serialize_rdt` delegates to `caliper_docgen_core::pipeline::rdt`, which the NAPI binding shares. Its `methods: []` field is a deliberate no-op documented inline: "this tool doesn't extract class methods, and RDT consumers (Storybook's docgen addon) only ever read it for class components" — not a placeholder for a future feature, a permanent constant matching what RDT-format consumers actually need. `rdt::type_json` reproduces RDT's specific `{"name": "enum", "value": [...]}` convention for literal unions specifically so prop-table renderers that pattern-match `type.name === "enum"` (a common Storybook addon integration point) render a `<select>` control — this is copying an external format's quirk deliberately, not house style bleeding in.

The `composes` field (react-docgen's own "props come from this type, listed by name instead of flattened" fallback for unresolvable types) was populated by the resolver but **used to be silently dropped by `serialize_rdt`** — the `rdt_output_includes_composes` test (`extract.rs:202-227`) and its comment block point at the resolver-side fix in `pipeline::tests::test_unresolvable_intersection_member_records_raw_type_in_composes` as the other half of that bug. If a new `ComponentEntry` field is ever added on the core side, check `pipeline::rdt` by hand — nothing enforces that every core field round-trips into this hand-written serializer, which is exactly the class of bug `composes` fell into.

## `schema.rs`'s drift-detection test

`schema_value()` (`schema.rs:7-99`) is a **hand-maintained** JSON Schema for `ExtractionOutput` — there's no `#[derive(JsonSchema)]` generating it from the real struct. The module doc comment names this precedent ("Hand-maintained per ADR-0002-style precedent") and pairs it with `schema_covers_every_field_name_the_real_output_serializes` (`schema.rs:117-211`), which builds a fully-populated real `ExtractionOutput`, serializes it, walks every key name that appears in the real JSON, and asserts each one appears somewhere in the hand-written schema string. This is a **name-presence check, not a shape/type check** — it would catch a field being added to `ComponentEntry` and forgotten in `schema_value()`, but it would not catch the schema describing the wrong _type_ for a field that already has the right _name_. Extending a field's type without touching its name passes this test silently.

## No language server

A `lsp` subcommand existed as a scaffold (framing and the initialize/shutdown/exit lifecycle, `hoverProvider: false`) and was removed: editors already get hover and completion from the TypeScript language server, and the value caliper adds, the documentation view of a component, is served to tools through the lazy session API instead. `docs/edge-cases.md` P1-2, P1-6 and P1-7 and `docs/root-cause-analysis.md` cluster 6 describe bugs in that scaffold and are kept as history. The bounded-framing code that `crates/tsc-client` ported from it lives on there.

## KNOWN GAPS

- **`docs/edge-cases.md` P3-1** (still open, cross-referenced above under Locked Design Decisions): the exit-code contract is fully enforced for `extract`/`check`, but `watch` always exits based on its own cumulative snapshot rather than ever being run non-interactively with a documented CI contract, and there's no `--strict` equivalent for `extract`/`watch`/`inspect` — only `check` has one. This is flagged as intentional-for-now but not independently justified beyond `check`'s explicit CI purpose.
- **`inspect.rs` and `watch.rs`'s startup banner bypass `output.rs`**, using raw `println!` calls directly for their tabular/banner output rather than routing through `output.rs`'s helpers (Invariant 2's note). This doesn't violate the stdout-is-payload-only half of the "no terminal code outside output.rs" rule in practice (neither writes JSON to stdout by default), but it is a literal deviation from `crates/cli/AGENTS.md`'s "never `println!` in command handlers" rule as stated, worth flagging as a possible follow-up rather than treating as settled.
- **`--json` on `extract` has no equivalent on `check`'s already-JSON-capable path worth double-checking for consistency** — `check --json` (`check.rs:21-22`) emits `output.diagnostics` directly (an array), while `extract --json` (`extract.rs:45-46`) emits the full `ExtractionOutput` (an object). These are two different JSON shapes under the same flag name across two commands; not a bug (each is documented for its own command), but worth knowing before assuming `--json` means the same payload shape everywhere in this CLI.
