# Resolver: type resolution

**Source:** `crates/core/src/resolver/mod.rs`, `crates/core/src/resolver/chain.rs`, `crates/core/src/resolver/alias.rs`, `crates/core/src/resolver/named.rs`, `crates/core/src/resolver/precedence.rs`, `crates/core/src/resolver/substitute.rs`, `crates/core/src/resolver/primitives.rs`, `crates/core/src/resolver/template.rs`, `crates/core/src/resolver/func.rs`, `crates/core/src/resolver/collected.rs`, `crates/core/src/resolver/extends.rs`, `crates/core/src/resolver/import.rs`, `crates/core/src/resolver/react.rs`, `crates/core/src/resolver/html.rs`, `crates/core/src/known.rs`, `crates/core/src/types/global.rs` (`ResolveState`), `crates/core/src/types/output.rs` (`OpaqueDetail`)

The resolver is phase 3a: `ComponentMapping` (raw, per-component collected data) plus `GlobalSourceData` (all files' merged interfaces/aliases/enums) go in; a fully resolved `ComponentEntry` with `PropType` props comes out. No string parsing happens here — everything arriving is already structured `CollectedType`/`CollectedTypeAlias`. Every unresolvable type becomes `PropType::Opaque` plus a `Diagnostic` — the module never fails outright, only degrades with a trace.

## Entry point and threading contract

```rust
pub fn resolve_component(mapping: &ComponentMapping, ctx: &ResolutionContext) -> (ComponentEntry, Vec<Diagnostic>)
```

This is called from inside a rayon `.map()` over every discovered component, in parallel. Per `crates/core/AGENTS.md`: _"All inputs must be owned or `Arc`-wrapped — no borrowed data crosses thread boundaries."_ This is a hard non-negotiable, not a style preference:

- `ResolutionContext` holds `Arc<GlobalSourceData>`, `Arc<ImportResolutionMap>`, `Arc<Resolver>` (the `oxc_resolver` instance) — cheap to clone, shared read-only across every worker thread.
- `ResolveState` (`types/global.rs:19`) is constructed fresh per `resolve_component` call via `ResolveState::default()` and threaded through every recursive call by `&mut` reference. It is **never** shared across components and carries no `Arc` — it's pure per-call mutable scratch state (visited-set, diagnostics accumulator, in-scope type params). If a future change tried to hoist `ResolveState` up to be shared across the rayon `.map()` (e.g. to dedupe diagnostics), that would silently corrupt cycle detection across unrelated components — the visited-set has no per-component reset mechanism, and two components racing on the same shared set would each see the other's visited entries and wrongly short-circuit.

## Module resolution

Every resolver of a run comes from `ModuleResolvers::new` (`resolver/mod.rs`), so the pipeline's `@types/react` lookup and the resolver find the same files. It resolves the way TypeScript does for the project:

- **tsconfig:** the configured one; otherwise `oxc_resolver` finds the nearest `tsconfig.json` above each importing file. That only works through `resolve_file`/`resolve_dts`, which take the importing file, not its directory.
- **`customConditions`** of the governing tsconfig (configured, or nearest above the first source directory), following `extends`, are added to the conditions. `oxc_resolver` does not read them, and workspaces such as React Spectrum's reach their packages' TypeScript sources only through them.
- **Extensions:** `.d.mts`/`.d.cts` resolve, and an import written as `./button.js` finds `button.ts`.
- **Declarations for a package** (`react::resolve_package_types_file`): `resolve_dts`, then a retry with only the `types` and custom conditions (`types_first`, for a package listing `"import"` before `"types"`), then `@types/<name>`. A declaration path that does not exist counts as none, so an unbuilt workspace package is reported as unresolved instead of resolving to a missing file.

**Invariant:** never build an `oxc_resolver::Resolver` for module resolution outside `ModuleResolvers`; a second configuration would resolve the same import to a different file.

## Dependency declarations (`load_dependencies`, ADR 0010)

With `PipelineOptions::load_dependencies`, `ResolutionContext::with_dependencies` attaches the run's `DependencyLayer` (`dependency_types.rs`). The resolver reads it only through fallbacks, so every lookup the project's own data answers is unchanged:

- **Import map and named-type index:** a file the project's maps don't hold is looked up in the layer's (`ImportResolutionMap::fallback`, `NamedTypeIndex::fallback`).
- **Re-exports:** `follow_reexports` takes the loader's answer for a `(module, name)` it walked, instead of walking the package's stubs again; a module with no answer is walked as before.
- **Precedence (ADR 0014):** a declaration, the project's or a loaded dependency's, then a known shortcut, then a builtin. At the props-chain level a declaration that evaluates to nothing (cva's `VariantProps`, which needs `Parameters<C>[0]`) gives way to a shortcut of the same name (`chain::known_fallback`), and its diagnostics are dropped with it.
- **Value index:** `ComponentProps<typeof X>` and `typeof X` in `extends` find a dependency component through `DependencyLayer::component`. Dependency components and enums live only in the layer's `GlobalSourceData`, so they never reach output or the bare-name indexes.
- **Const arrays:** `(typeof X)[number]` reads `X` as the symbol in scope in the file that wrote the type, project or dependency (`NamedTypeIndex::lookup_const_array`, with the dependency layer as the fallback), then the project's array of that name. An array is an `as const` literal or a `declare const X: readonly ["a", "b"]` annotation, which is how Radix declares `Align` and `Side`.
- **Diagnostics:** a type the loader could not find says why in the help of "Cannot resolve type" (`unresolved_type_help`): the module did not resolve, resolved to JavaScript without types, or does not export the name.

- **Collapse** (`collapse_inherited_props`, ADR 0012): `ctx.collapses` records an inherited source declaring more than 30 props as an `InheritedLayer` (no `html_element`, `total_props` = its declared count) and resolves only its notable members (`notable_html_attrs`' element-independent list) into `notable_inherited`. Sources are an interface's own members and an object-literal alias; an interface's parents are sources of their own. Never at depth 0 (the component's own props type), and never while `ResolveState::expand_all` is set: `Pick`'s base and `keyof` operands select or count props by name. `Dependencies` (default) collapses loaded dependency files only; `All` adds every file outside `node_modules`, so React's and TypeScript's declarations stay with `html_attributes`. Interface-chain recordings are keyed on `expand_all` too.

**Invariant:** never merge layer data into the project's `GlobalSourceData`; that would emit dependency components and enums and let dependency names shadow project names in bare-name lookups.

## Wrapper callees (`resolver/callee.rs`)

A component built by a generic call (`wrapperTypeArgument`, or `hocWrapper` with type arguments, as in `factory<Payload>((props: P) => …)`) has the props its callee's result type declares; the props type its detection selected is the fallback when the callee or its result's props can't be evaluated. The extractor records every generic function's result in `SourceData::function_results`: the return annotation, or the type its only top-level `return … as T` asserts. `callee::result_chain` binds the callee's type parameters to the call's type arguments, follows aliases to the first React component type (`NamedExoticComponent<P>`, `FC<P>`, a call signature, …) and resolves P as the props chain (`Payload['props'] & RefAttributes<…> & { component?: any; … }`, through `evaluate.rs`). A name two members declare intersects, and `any` absorbs the intersection. When P resolves to nothing (a conditional over an unbound generic, as in `polymorphicFactory`), the selection stands. The callee's file is a recorded dependency, so editing the factory re-resolves the components it builds; `follow_reexports` counts any declaration a file exports, so `export *` barrels reach it. The extractor's guesses among type arguments (a `props` payload member, a `*Props` name) now only decide detection: they reject 10 candidates across the five benchmark corpora.

**Gap:** a result type asserted through an alias declared inside the function body (Mantine's `polymorphicFactory`) is not reachable.

## Evaluating a props base with known operands (`resolver/evaluate.rs`)

`resolve_base_as_chain` evaluates three kinds of props base when their operands are known, without a checker: a conditional whose check is a literal and whose constraint is `keyof X`, a literal or a union of literals (`RecipeProps<"button">` picks its branch); an indexed access, chained and through generic interface members and aliases (`ConfigRecipes["button"]["__type"]`); and a mapped type over `keyof X` or a literal union, one prop per key with the key variable bound. A homomorphic mapped type without `?`/`-?` keeps each source member's optionality and description. Anything else (an `infer`, an unbound generic) evaluates to `None` and keeps the warning and `composes` entry. `alias_display` uses the same evaluator for an argument that reads a member (`ConditionalValue<ButtonVariant["size"]>` prints the member's type), and so does any indexed access at the type level (`primitives::resolve_indexed_access`), before the `CSSProperties`/`HTMLAttributes` member table, which answers only when no declaration does (ADR 0015). A member read binds each ancestor's `extends` arguments to the arguments it was reached with, so `CSSProperties["width"]` through `Properties<string | number>` gets `Width<string | number>`. It also reads curated mode's React index and treats an unimported `React.X` as React's UMD global. A member read goes through an ancestor that is an alias, and through a mapped type over `keyof T` with the key bound (csstype's `Fallback<T>`); a conditional whose check is a member read is decided when that member's type is a set of string types, and a member the payload object doesn't declare takes the false branch. Type-level conditionals use the same evaluator, which decides assignability over one small set of atoms (`Atom`: literals, `string`, `number`, `boolean` as `false | true`, `null`, `undefined`) on both sides. A generic alias that is a conditional over a bare type parameter distributes over the members of the argument bound to it (`named::expand_alias`, `evaluate::distributive_param`/`union_members`), as TypeScript does for a naked type parameter: each member is evaluated alone and the results united by `primitives::union_of`, which drops `never`. This is how `Exclude` and `Extract` are read: from the project's `lib.es5.d.ts` (`named::evaluate_lib_alias`, in a detached state whose diagnostics are kept only when everything evaluates), not by name, and a project's own `type Without<T, U> = T extends U ? never : T` works the same. `T & {}` removes `null` and `undefined` (`NonNullable`). Template literals expand number and boolean parts. A generic alias whose expansion has more than `MAX_EXPANDED_NODES` nodes prints by name with its arguments evaluated as far as they go (`Responsive<DimensionValue>`), the way TypeScript and react-docgen-typescript print it. Each omitted type argument takes its parameter's declared default (`bind_args`, `SourceData::type_param_defaults`). A cycle key is a hash of the arguments' structure (`CollectedType::structural_hash`), not their debug text. The evaluator counts only its own steps (its callers start it at 0), and caches top-level member reads per run with the files they read (`ResolutionContext::member_reads`). Lookups record their files, so editing the declarations re-resolves dependents.

## The three-tier data model this resolver operates on

- `CollectedType` / `CollectedTypeAlias` — what the extractor produced: structural, not yet resolved, may reference cross-file names.
- `PropType` — resolved output type at the _type level_ (an interface reference becomes a bare `PropType::Named`, never expanded here).
- `ResolvedChain` (`resolver/mod.rs`) — resolved output at the _chain/component level_: `props: Vec<ParsedProp>`, `inheritance: Vec<InheritedLayer>`, `composes: Vec<String>`, `discriminant_prop: Option<String>`. This is the accumulator a props-providing type (interface, intersection, discriminated union) produces; it's private to the resolver module (`struct ResolvedChain`, not `pub`).

**Invariant 1 — an interface name resolves differently depending on which level asked.** At the type level (`resolve_named`, called for a _field's_ type — e.g. `value: SomeInterface`), a matched interface returns `PropType::Named { name, args }` — bare, unexpanded. At the chain level (`resolve_props_chain`, called for a _props-base_ type — the component's own props type, or an `extends` target), the same interface expands via `resolve_interface_chain` into real `ParsedProp`s. This split exists because a field whose type happens to be an interface should show as a named type reference in RDT-compatible output, not get flattened into an anonymous object — but a component's _own_ props type (or something it extends) must actually contribute fields. Conflating the two would either over-expand nested interface-typed fields into inline objects, or under-expand a component's own extends chain.

## Locked design decision: source-before-known-pattern precedence (P0-1)

`resolver/precedence.rs`'s `resolve_source_defined_or_known` is the **only** place either `chain.rs` or `named.rs` may implement "how does a bare type name resolve." It checks, in this exact order:

1. `resolve_to_canonical` — follow imports/re-exports/barrel files to the real declaring `(file, name)`.
2. `lookup_type_alias` at that canonical location.
3. `lookup_interface` at that canonical location.
4. `resolve_known` — the hardcoded library-pattern shortcut table in `known.rs` (SxProps, VariantProps, HTMLChakraProps, …).

**Why this order, and why it's locked:** a project can legitimately declare its own `interface SxProps { customSx: string }` that has nothing to do with MUI. If `known.rs`'s hardcoded SxProps shortcut were checked before the project's own source, that project-defined interface would be silently replaced by the opaque MUI shortcut — the component's real, resolvable prop (`customSx`) would vanish with no trace. `named.rs` always had this order right and documented it as intentional. `chain.rs`'s `extends`-clause path (used when a project's `interface Foo extends SomeName`) independently re-implemented the same sequence and got it backwards — checking `resolve_known` _before_ the project's own interface/alias lookup. Nothing tied the two orderings together, so `chain.rs` was free to drift the moment it was written (see `docs/root-cause-analysis.md` §8). This is the confirmed P0-1 bug; `precedence.rs` was extracted specifically to make that drift structurally impossible — both call sites now share one function, so reordering one without the other can't happen again.

A regression test locks this at both the shared-function level (`precedence.rs`'s `source_defined_interface_wins_over_a_known_pattern_shortcut`) and end-to-end through the extends path (`mod.rs`'s `test_extends_clause_prefers_project_defined_sx_props_over_known_shortcut`).

**Documented residual divergence (not a bug, but don't call the two functions "unified"):** `chain.rs` and `named.rs` still differ in two respects the P0-1 fix didn't touch — `named.rs` checks React-builtin status _before_ canonical resolution, `chain.rs` checks it _after_ the known-pattern block; and `chain.rs` checks `is_ts_utility_type` very early (step 1, before known-pattern), while `named.rs`'s analogous check runs last (step 6, after interface/alias/known-pattern). Neither divergence reproduces the P0-1 shape (a user-defined type being shadowed by a shortcut), so they were explicitly left out of scope. If a future change touches either ordering, re-verify this claim rather than assuming it's still accurate — the flagging note lives in `root-cause-analysis.md` §8, not in code.

## Locked design decision: `give_up` vs `new` for `OpaqueDetail`

`PropType::Opaque`'s payload (`OpaqueDetail`, `types/output.rs:324`) is private outside its own module and has exactly two constructors:

- `OpaqueDetail::give_up(state: &mut ResolveState, raw, reason, diagnostic)` — pushes `diagnostic` onto `state.diagnostics` _and_ builds the value in one call. This is the sanctioned path for every real resolver call site (`collected.rs`, `chain.rs`, `named.rs`, `func.rs`, `primitives.rs`, `template.rs`) — a call site literally cannot construct an opaque value without being forced to also explain why, at the same call site, so "degrade silently" is not an available mistake to make there.
- `OpaqueDetail::new(raw, reason)` — builds the value with **no** diagnostic push. Used exclusively by `known.rs`.

**Why the split exists:** `known.rs` has no `ResolveState` to push into — and per the top-level `AGENTS.md`'s "no reverse dependencies" rule (`resolver` depends on `types`/`known`, never the other way), `known.rs` must not depend on `resolver::ResolveState` just to gain a diagnostics channel. So `known.rs` builds bare `OpaqueDetail`s via `new`, and the _caller_ (`chain.rs` step 2 / `named.rs` step 5, both of which do have a live `ResolveState`) is responsible for detecting `KnownPatternResult::Type(PropType::Opaque(detail))` and calling `known::push_known_opaque_diagnostic(&mut state.diagnostics, detail.reason(), type_name, file)` right after. This was itself a fixed gap (an adversarial-review finding, tests `test_known_opaque_result_emits_diagnostic_at_type_level` / `_at_chain_level`) — a `KnownPatternResult::Type` that happened to be `Opaque` (ThemingProps, StylesApiProps, cva/tv without discoverable variants) used to degrade with zero diagnostic, unlike every other opaque-producing path. **Invariant 2:** any new `known.rs` match arm that can return `KnownPatternResult::Type(PropType::Opaque(_))` relies on both call sites' existing post-match check to surface it — a third call site into `resolve_known` that skips this check would silently reintroduce the exact bug the two existing tests guard against.

## Cycle detection: scope and limits

`resolve_props_chain` (chain.rs) is the only place with an explicit visited-set check:

```rust
let visit_key = format!("{}:{}<{}>", consuming_file, type_name, type_args.join(","));
if !state.visited.insert(visit_key) { return ResolvedChain::give_up(...) }
```

**Invariant 3 — the visited key is `(file, type_name, type_args)`, not `(file, type_name)` alone.** This was a real bug (see `test_two_distinct_partial_extends_targets_both_resolve`): `interface TableProps extends Partial<RowHeights>, Partial<ColumnWidths>` needs both `Partial<RowHeights>` and `Partial<ColumnWidths>` to resolve independently. A bare-name visited key would treat the second `Partial<...>` as "already visited" (colliding on `"Partial"`) and silently drop `ColumnWidths`'s contribution with zero diagnostic. Any future change to the visit-key construction must preserve `type_args` in the key or this regression returns.

**What this cycle detection catches, and what it doesn't:**

- It catches genuine self-reference at the _chain_ level: an interface's `extends` clause (directly or transitively) referencing itself (`test_self_referential_extends_emits_diagnostic_instead_of_silent_default`), and a props-base type alias cycling back to itself.
- It does **not** catch cycles at the _named-type_ level (`resolve_named` in `named.rs`) — that function has no visited-set of its own. A field-level cycle (e.g. `type A = { self: B }; type B = { self: A }` referenced only as field types, never as a props base) is instead bounded only by `MAX_DEPTH`, not detected as "circular" with the more specific diagnostic — it degrades to a `MaxDepthExceeded` opaque once depth runs out, without ever getting the `DiagnosticCode::MaxDepthExceeded`-with-circular-reference-hint treatment the chain-level path gets pre-emptively. This is a real asymmetry, not an oversight documented anywhere else — a future contributor "fixing" `resolve_named` to add its own visited-set would need to reconcile it with the fact that fields legitimately reference the same interface repeatedly in siblings without that being a cycle (e.g. two props both typed `Theme`), so any fix needs _reference identity_ awareness, not blanket revisit-once semantics.
- Branch-local cycle detection: `resolve_union_alias` (alias.rs) and the `Omit<T, keyof U>` structural handling both clone `state.visited` into a throwaway `branch_state` before probing a union member or a `keyof` operand, then merge only the diagnostics back — never the visited-set. This is deliberate: a union member (or the `U` in `Omit<T, keyof U> & U`) is very often _also_ resolved for real elsewhere in the same alias, and sharing the main visited-set would mark it "already visited" during the branch probe and make the real, later resolution come back empty. **Invariant 4:** any new speculative/probing resolution (resolving something just to inspect its shape, not to keep its output) must clone `state.visited` into a branch-local `ResolveState`, never mutate the shared one — this is the established idiom, not incidental to these two call sites.

## `MAX_DEPTH` — purpose and how it differs from the extractor's guard

`MAX_DEPTH: u8 = 20` in `resolver/mod.rs` bounds _recursive resolution depth_ — every recursive entry point (`resolve_props_chain`, `resolve_named`, `resolve_collected_type`) checks `depth > MAX_DEPTH` and degrades to an opaque `MaxDepthExceeded` diagnostic via the shared `max_depth_diagnostic` helper. This exists to bound **type-graph traversal depth** — how many named-type hops (interface → extends → interface → alias → …) resolution will follow before giving up — which is a different axis than the extractor's `MAX_SOURCE_NESTING_DEPTH` (mentioned in `template.rs`'s doc comment as an analogous guard), which bounds **source-AST nesting depth** during a single file's parse (e.g. deeply nested object/array literal syntax in one type expression). A pathological type could be shallow in source-AST terms but deep in resolution-graph terms (a long `extends` chain across many files) or vice versa (one file with deeply nested inline object types but no cross-type references at all) — the two guards are not interchangeable and both are needed. `MAX_DEPTH` is deliberately `u8` (max 255), reinforcing that 20 is a "this smells like a cycle, not a legitimately deep type" threshold, not a hard safety ceiling sized for worst-case input.

Depth decides a result only through that limit and through `depth > 0` (collapse, above), so the interface-chain and named-type memos (`resolver/memo.rs`) key a recording on `depth > 0`, `expand_all` and `keys_only`, not on the depth itself. Every check against the limit goes through `past_max_depth`, which keeps the deepest depth checked in `ResolveState::depth_high`; a recording stores how far past its starting depth that reached. It answers a state that starts anywhere its deepest check still stays within the limit, and, if a check hit the limit (the result holds a depth-exceeded stop), only a state that starts at the same depth. A new place that compares a depth against `MAX_DEPTH` must call `past_max_depth`, or a recording made near the limit would be reused where the limit is not reached.

The cycle sets (`visited`, `named_in_progress`) and the recordings' read logs hold ids of the `file:name<arguments>` keys (`key_id` in `types/global.rs`), not the strings: copying a set or a log for a branch or an enclosing recording copies numbers, and no reference count is shared between the threads resolving components. Ids are process-wide and never reused, so equal ids are equal keys.

A separate, unrelated cap exists in `template.rs`: `MAX_TEMPLATE_LITERAL_EXPANSIONS = 4096`, bounding the Cartesian product of a template literal's per-part alternatives (each part can be a union with many members, so the product is exponential in part count) — this is a _combinatorial_ guard, not a recursion-depth guard, and uses the same "cap, then degrade to Opaque with a diagnostic" shape as `MAX_DEPTH` without being the same mechanism.

## Generic substitution: what works, what's known-incomplete

`substitute.rs` implements **purely structural** substitution for user-defined generic type aliases (`type Assign<T, U> = Omit<T, keyof U> & U`) — no type inference, no conditional-type evaluation. Two entry points:

- `apply_generic_args` — call-site arguments arrive as _display strings_ (`type_args: &[String]`, the chain-level resolution path's historical shape) and get recovered into `CollectedType` on a best-effort basis via `raw_arg_to_collected_type`, which only recognizes plain identifiers and quoted string literals — anything with nested generics, unions, etc. is preserved as an opaque `CollectedType::Raw` string, not actually substituted.
- `generic_alias_with_structured_args` — used when the caller already has a _structured_ `CollectedType` argument (e.g. `SelectRootBaseProps<T>` passed as another generic alias's own argument) — skips the string round-trip entirely, so nested generics and `keyof` operands survive substitution intact. `resolve_base_as_chain` (alias.rs) prefers this path when available, falling back to the string-based path only when arguments are already flattened to display strings.

**Invariant 5:** `build_substitution` silently drops trailing unfilled type parameters when a call site under-applies a generic alias (`Foo<string>` for `type Foo<T, U> = ...` — `U` is left unsubstituted) but as of the current code **does** push a `DiagnosticCode::GenericArgumentMismatch` warning naming the unfilled params (test: `build_substitution_diagnoses_unfilled_trailing_type_params`) — this was fixed from an earlier fully-silent version; `root-cause-analysis.md`'s standalone-findings table still describes the pre-fix "silently truncates" behavior and is stale on this specific point relative to current code. Verify against the live diagnostic before citing that table entry as still-open.

**Known, documented incomplete case — Ariakit's `Props<T, O>` pattern.** `docs/benchmarks.md` root-causes 6 of 10 outlier components (Ariakit, ark-ui, storybook-emotion, fluentui) in one benchmark corpus to generic-alias substitution not matching the pattern _at all_ — further upstream than anything `substitute.rs` currently handles. Ariakit's own shape is `type Props<T, O> = O & Omit<ComponentPropsWithoutRef<T>, keyof O>`, requiring substituting `T = "button"` through a _nested_ `Omit` + `ComponentPropsWithoutRef` chain where `ComponentPropsWithoutRef` itself is a React builtin needing its own args substituted before it can resolve to an `HtmlAttributes` shape. The existing machinery handles single-level generic aliases whose body is directly `Omit<T, keyof U> & U` (covered by `test_generic_type_alias_substitution`); it does not yet chase a generic parameter through an intermediate builtin generic. This is an open gap, not a design decision — don't read the existing substitution machinery as "handles generics," it handles one well-tested shape of generics.

## Give-up discipline: `ResolvedChain`'s two "this contributes nothing" constructors

Mirroring the `OpaqueDetail` split at the chain level: `ResolvedChain::empty()` is the base accumulator every real resolution path builds up from (interface chain resolution, extends merging). `ResolvedChain::empty_with_compose(type_name)` and `ResolvedChain::give_up(type_name, diag, state)` are the two sanctioned "this type contributes nothing further" signals — `give_up` additionally pushes a diagnostic first. **Invariant 6:** every give-up path in `chain.rs`/`alias.rs` must go through one of these two, never a bare `ResolvedChain::default()` — a bare `default()` was itself a fixed bug (`test_self_referential_extends_emits_diagnostic_instead_of_silent_default`, `test_literal_union_as_props_base_emits_diagnostic_instead_of_silent_default`): the cycle-detected branch and the literal-union-as-props-base branch both used to return a silent empty chain with no trace. `composes` — react-docgen's own field for "props come from this type, named instead of flattened" — is populated by every give-up path today specifically so a degraded resolution still surfaces _something_ in RDT-compatible output rather than silently vanishing to zero props.

## Known gaps (cross-referenced, not re-derived)

These are documented elsewhere and intentionally not re-litigated here:

- **Generic substitution through nested builtin chains** (Ariakit `Props<T, O>` and 5 siblings) — `docs/benchmarks.md`, "Corsa-deferred" generic-parameter-substitution item.
- **`composes` as a stop-gap, not a fix** — `docs/benchmarks.md` explains `composes` population closes the _symptom_ (silent zero-props output) for type-checker-boundary failures, not the underlying inability to expand conditional/mapped/indexed-access types without a real checker.
- **Resolver precedence's two residual (non-P0-1) divergences** between `chain.rs` and `named.rs` (React-builtin-check ordering, `is_ts_utility_type` check ordering) — `docs/root-cause-analysis.md` §8, explicitly flagged as open follow-up, not fixed by the P0-1 precedence extraction.
- **The type of a value built by a call** (`z.infer<typeof schema>` with `const schema = z.object({ ... })`; a store, a hook's result). `typeof X` is a type here only for components, cva variants and `as const` arrays (and now `declare const X: readonly [...]`). TypeScript infers the call's generic arguments from its argument expression and then evaluates the library's conditional and mapped types; that needs the checker (ADR 0006), so the prop stays a named reference (`Event["name"]`) with an Info `OPAQUE_TYPE` diagnostic whose help names the remedy: declare the type where it is used, or `--experimental-semantic-types`. shadcn's `CopyButton.event` is the example.
- **`resolve_named`'s lack of its own cycle-detection visited-set** (this document's Invariant 3 discussion) — not tracked in either doc today; flagging here as a genuine gap surfaced while writing this file, worth a follow-up note in `root-cause-analysis.md` if a future audit revisits cycle detection.

## Other structural notes worth knowing before touching this code

- **`AtFile` is a substitution-tracking marker, not a resolvable type.** `CollectedType::AtFile { file, inner }` says "`inner` was written in `file`, not whatever file this call chain has been resolving relative to" — created when a generic argument is substituted from the caller's scope into a callee alias declared elsewhere. Every dispatch site (`resolve_base_as_chain`, `resolve_collected_type`, `substitute_type`) must switch file context to `file` before recursing into `inner`, or same-file lookups silently resolve against the wrong file.
- **Union alias members resolve relative to the alias's _own_ declaring file, not the caller's consuming file** (`resolve_type_alias_type`'s doc comment, `test_union_alias_members_resolve_relative_to_alias_own_file_not_caller`). A `type Combined = A | B` alias imported cross-file still has `A`/`B` as same-file siblings of `Combined` wherever `Combined` itself is declared — using the caller's file produces spurious "Cannot resolve type 'A'" diagnostics for names that were never meant to be looked up relative to the importer.
- **A generic interface/alias's own declared type parameters must be registered before its body is resolved**, via `ctx.global.interface_type_params` / `type_alias_params` feeding `state.in_scope_type_params` — otherwise `TData`, `T`, `U`, etc. read as unresolvable named types with a spurious warning instead of being recognized as expected, unexpandable placeholders (`test_generic_interface_own_type_params_suppress_diagnostic`).
- **A referenced alias over a type the resolver can't evaluate keeps its name.** When an alias's expansion holds an `Opaque` conditional, mapped or indexed access type (`z.infer<typeof schema>` is `typeof schema["_output"]`), or an alias already named for that reason, `named.rs`'s `alias_display` returns `Named` with the arguments as written (`StyleProp<MantineSpacing>`), as TypeScript prints it, instead of the source text. Literal unions and other fully evaluated expansions still expand, and so does an object at the top level. `ResolveState::named_unevaluated` carries the "already named" fact up to enclosing aliases; it is taken before each alias's expansion and OR-ed back after (`test_an_alias_over_an_unevaluated_type_keeps_its_name`).
- **Curated vs Full vs None `HtmlAttributeMode`** changes _where_ HTML-attribute expansion happens, not whether an `InheritedLayer` is recorded — in Curated mode `resolve_component` synthesizes a small curated subset (`notable_inherited`) from `react_types::notable_html_attrs`; in Full mode `extends.rs`'s `real_html_attrs_chain` looks up the actually-merged `@types/react` interface and expands it for real into own props; in None mode neither happens. This is orthogonal to the resolver's normal source-vs-known precedence — it's a pipeline-level configuration knob threaded through `ResolutionContext`, not a resolution-order decision.
