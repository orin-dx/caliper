# Caliper v1 review

My release assessment: the project has a credible speed advantage and much better structural coverage than it had a week ago, but the current open stack is not yet a v1 quality gate. I would continue the staged releases in the roadmap (https://github.com/orin-dx/caliper/blob/08bafb04/docs/projects/architecture-roadmap.md), while treating watch correctness, detection precision, and a reproducible RDT comparison as required evidence before calling the output dependable for v1.

I reviewed the 20 PRs merged since October 14, all 20 PRs open on October 21, the final stacked branch, architecture and ADRs, tests, CI, and release workflow. This was a code and CI review; I did not run a new local build or benchmark. The working tree already contains uncommitted changes, which I left untouched. Entire transcript search could not read its saved Keychain login, so the retrospective relies on commits, PRs, and repository documents.

## What the week accomplished

The merged work renamed and published the Caliper packages, changed package metadata and licensing, updated dependencies, separated large inline Rust test modules, added architecture tripwires, and tightened production lints. The open stack then addresses real defects: deterministic enum selection, unreadable files, diagnostic codes, generic Pick/Omit, barrel resolution, watch parity, and several missed component declaration shapes. These are substantive improvements, and CI is green across the dependent stack.

The measured direction is promising. The roadmap’s latest source-only comparison (https://github.com/orin-dx/caliper/blob/08bafb04/docs/projects/architecture-roadmap.md) reports component recall against RDT of 93% for Mantine, 92% for Chakra, 97% for Ant Design, 98% for shadcn/ui, and 99% for react-spectrum after #69. Those numbers establish progress on recall in that sample. They do not yet establish precision, output equivalence with dependencies installed, or v1 reliability under incremental updates.

## Findings ranked for release

| Priority | Finding and evidence | Consequence and action |
|---|---|---|
| P0 | The new wrapper rule can emit non-components. #62 (https://github.com/orin-dx/caliper/pull/62) accepts a PascalCase binding when a generic call has a plausible first argument, including any string or identifier; it does not inspect the callee’s return type. A local interface or a type ending in Props is enough to select props (wrapper.rs, lines 43–55 and 105–120 (https://github.com/orin-dx/caliper/blob/08bafb04/crates/core/src/extractor/wrapper.rs#L43-L120)). For example, a Button constant returned as a string by makeLabel<ButtonProps>("button") meets these conditions. | This can inflate recall and pollute consumer output. Before enabling this rule as a default v1 behavior, run the roadmap’s per-family, hand-labeled precision gate, add representative non-component calls, and prefer callee evidence where available. |
| P0 | Watch snapshots can combine different revisions. #67 (https://github.com/orin-dx/caliper/pull/67) repairs several parity bugs, but global, reverse dependencies, named types, components, and diagnostics still publish separately. update_file swaps global, then independently updates the other stores (watch.rs, lines 180–212 and 241–301 (https://github.com/orin-dx/caliper/blob/08bafb04/crates/core/src/pipeline/watch.rs#L180-L301)); snapshot() reads them separately (lines 129–150 (https://github.com/orin-dx/caliper/blob/08bafb04/crates/core/src/pipeline/watch.rs#L129-L150)). Concurrent updates can also load a global revision other than the one whose named-type index a call just patched. | HMR consumers can observe stale or mixed props and diagnostics. Implement the documented immutable WatchRevision publication model, then test concurrent old-or-new complete snapshots and clean/incremental equivalence. Serializing updates is a reasonable interim containment measure. |
| P1, confirmed by control flow | Initial watch diagnostics disappear from later snapshots. initialize() receives output from cold extraction and seeds component_cache, but never seeds self.diagnostics; snapshot() reads only that map plus enum diagnostics (watch.rs, lines 110–150 (https://github.com/orin-dx/caliper/blob/08bafb04/crates/core/src/pipeline/watch.rs#L110-L150)). | A cold parse or I/O error is returned once and then absent from watch --out snapshots until an update replaces it. Add an exact initial-output versus snapshot diagnostic test and persist the cold diagnostics. |
| P1, confirmed by control flow | The Vite virtual module retains removed or renamed components. On HMR, the plugin only assigns updatedComponents into currentOutput.components; it has no removal path (index.ts, lines 175–184 (https://github.com/orin-dx/caliper/blob/08bafb04/packages/vite-plugin/src/index.ts#L175-L184)). Rust #67 evicts a changed file’s old cache keys, but the incremental payload does not convey those removals. | A renamed Card can leave Card beside Panel in the virtual module. Return removed keys or a file-scoped replacement and test rename, deletion, and a component that stops resolving. |
| P1, confirmed by control flow | A recorded wrapper candidate can vanish without a diagnostic. try_record_wrapper_call returns true, preventing the normal skip diagnostic. During promotion, select_wrapper_props returning None simply continues (wrapper.rs, lines 60–89 (https://github.com/orin-dx/caliper/blob/08bafb04/crates/core/src/extractor/wrapper.rs#L60-L89)). | This breaks the project rule that degradation is diagnosed. Emit a positioned diagnostic for a rejected recorded candidate, with care to avoid flooding users with ordinary non-components. |
| P1, semantic defect | #69 substitutes generic parameter names inside quoted text. Its substitute_identifiers scans identifier characters without tracking TypeScript string literals (chain.rs in #69 (https://github.com/orin-dx/caliper/pull/69/files)). For interface Wrap<T> extends Pick<Base, "T">, substituting T = number also changes the key string "T" to "number". | This can select the wrong inherited props while appearing resolved. Substitute on CollectedType nodes, as the roadmap already calls for, or at minimum make the temporary parser quote-aware and add this exact regression. |
| P1, release evidence | The RDT advantage is not yet proved end to end. The new shape test (https://github.com/orin-dx/caliper/blob/148bf3ab/crates/core/tests/shapes.rs) checks exact component and prop names on synthetic cases. It does not gate corpus precision, types, required flags, defaults, diagnostics, dependency-installed projects, or latency. just recall in the roadmap is not implemented. Existing benchmarks.md (https://github.com/orin-dx/caliper/blob/c32772ff/docs/benchmarks.md) is dated July and reports different figures and old package names from the October README. | Make one versioned, reproducible scorecard for the five corpora: recall, precision, exact prop fields, degradations, wall time, peak memory, and clean/watch parity. State the hardware, dependency state, tool versions, and comparison mode beside every claim. |

### Architectural issues

1. The semantic model is still partly text. ComponentMapping and ExtendsRef carry type arguments as strings; #69 adds a parser that reconstructs unions, intersections, arrays, and generic references from display text. This improves cases now but preserves the failure class behind D1 and creates a second TypeScript grammar in the resolver. Complete roadmap item 2.1, Vec<CollectedType>, before building more wrapper and backend behavior on this path. #69 (https://github.com/orin-dx/caliper/pull/69)
2. Detection provenance is partial. #60 (https://github.com/orin-dx/caliper/pull/60) adds DetectionRule, but classification still uses a first-success Option chain and a later wrapper promotion pass (visit.rs, lines 229–261 (https://github.com/orin-dx/caliper/blob/08bafb04/crates/core/src/extractor/visit.rs#L229-L261)). There is no common typed Detection { Component, Skip, NotCandidate } contract yet. That makes rule precedence, declined candidates, and diagnostics harder to reason about as more shapes are added.
3. ADR 0007 needs a precise merge contract. ADR 0007 (https://github.com/orin-dx/caliper/blob/08bafb04/docs/adr/0007-backend-discovers-components-and-compiles-in.md) says a structural entry wins on a discovery clash; ADR 0006 (https://github.com/orin-dx/caliper/blob/c32772ff/docs/adr/0006-semantic-backend-as-second-resolver.md) and the backend design say semantic props replace incomplete structural props. These can coexist only if “discovery clash” and “prop completion” are distinct operations. Define that distinction and its tests before wiring the backend. Likewise, schemaVersion should identify the output contract; use separate provenance to tell consumers which backend ran.
4. A layering back edge remains. The resolver still imports pipeline::HtmlAttributeMode (resolver/mod.rs, line 142 (https://github.com/orin-dx/caliper/blob/08bafb04/crates/core/src/resolver/mod.rs#L142)), contrary to the stated crate/module direction and roadmap 2.3. Move resolver configuration into the shared types boundary before adding backend merge logic.
5. Watch performance lacks a current gate. Every update clones GlobalSourceData inside ArcSwap::rcu (watch.rs, lines 186–190 (https://github.com/orin-dx/caliper/blob/08bafb04/crates/core/src/pipeline/watch.rs#L186-L190)), rebuilds reverse dependencies, and constructs a resolution context. It may be acceptable at today’s corpus size, but the claimed roughly 2 ms edit path needs measurement after the fixes and on large dependency-installed projects. Profile allocation and peak memory before changing data structures.

### Rust, security, and maintainability

- The stronger lint and architecture tests are good safeguards. I did not find evidence of a production unwrap() violation in the reviewed stack. There is a small consistency miss: an internal std::collections::HashMap remains in pipeline collection where project rules call for FxHashMap (pipeline/mod.rs, line 379 (https://github.com/orin-dx/caliper/blob/08bafb04/crates/core/src/pipeline/mod.rs#L379)).
- The tests added for watch parity compare components and enums in their visible() helper, omitting diagnostics (watch/tests.rs, lines 949–952 (https://github.com/orin-dx/caliper/blob/08bafb04/crates/core/src/pipeline/watch/tests.rs#L949-L952)). That omission is directly relevant to the initial-diagnostics defect.
- The real Vite/native integration tests are designed to skip when no locally built .node file exists. CI’s test-ts recipe runs the plugin unit suite; green CI therefore does not prove the real binding and plugin operate together on the release artifacts. Run those integration tests against a built native addon in at least one CI lane.
- I found no confirmed exploitable security vulnerability in this review. The exposed inputs still deserve a release-specific robustness gate: malformed TS, cache decoding, process framing, and package install behavior. The roadmap’s proposed property/fuzz work was deferred by #53 (https://github.com/orin-dx/caliper/pull/53); its golden cache layout test guards format changes, not arbitrary malformed data.
- Documentation drift is now a DX issue. docs/STATUS.md still says September and “fully tested”; the architecture notes still describe some already-fixed watch behavior; MIGRATING.md and docs/benchmarks.md retain the old name. A user comparing Caliper with RDT should encounter one current set of commands and claims.

## Recommended v1 sequence

1. Land the correctness stack in order, with focused fixes for #69’s quoted-key substitution and #62’s rejected-candidate diagnostic and false-positive gate.
2. Make watch output coherent, then verify exact components, props, enums, diagnostics, rename/removal behavior, and concurrent snapshots against cold extraction. Include the Vite virtual module in that gate.
3. Publish a reproducible Caliper-versus-RDT scorecard. Lead with accuracy and precision at a stated mode, then speed and memory for the same projects. Keep the structural default and opt-in checker results separate.
4. Finish the type-argument and detection contracts before integrating the TypeScript backend. Settle ADR 0007’s merge and provenance rules first.
5. Run release-artifact tests and refresh user docs before labeling v1: native addon plus Vite integration, platform package installation, current CLI/API guides, and one maintained benchmark page.

Caliper’s strongest value proposition is already visible: fast structural extraction with useful diagnostics and incremental access. For v1, the decisive proof is that those advantages survive real library shapes, false-positive review, file edits, and packaged installation with results a user can reproduce.

I've read the trails overview and the gates page.

What trails are:
- A trail replaces the pull request in Entire's model. It holds the intent (title, description, type, priority), the linked branches (changes), the agent sessions, and the review evidence.
- A change is one linked branch in one repo. Each change merges separately. The trail has open and closed status, and "Planning" is the phase before any branch is linked.
- For GitHub mirrors, CI and merging still run through a linked PR. Entire review and GitHub review are separate and both must pass.

Gates: these are per-repo merge requirements, set under Settings → Gates:
- Up to Date: the branch is current with its base.
- Human Review: a minimum number of approvals, and whether a push resets them.
- Agent Review: unresolved findings from the trail-review runner, blocking at a severity threshold you choose.
- Checks: GitHub CI.

What this means for your scoping question:
- The recommended workflow starts by capturing the intent: problem, outcome, acceptance criteria. So a trail should be feature-sized with a done state, which confirms you were right about "v1 hardening".
- A trail can link several branches, so the stack (#391, #393, #397, #398) could be one trail with four changes. I'd try that on the release-recovery group first. I'm inferring this from "changes across repositories and branches". The docs don't show several same-repo branches on one trail.
