# caliper-docgen-semantic

## 0.5.0

_2026-11-14 · [compare](https://github.com/orin-dx/caliper/compare/caliper-docgen-semantic@0.4.0...caliper-docgen-semantic@0.5.0)_

### Minor Changes

- The built-in checker is guarded so that it does not take Storybook or the CLI down with it. A panic inside it fails only the request that caused it; the session it unwound through is closed and a fresh one answers the next request (after three, the checker stays off for the session, as for a crashed process). A file nested more than 20,000 brackets deep is not given to it, since `tsrs` overflows its parse stack and aborts the process at a few hundred thousand: the components that read it keep their structural answer with a warning naming the file. Its memory is now bounded: past 768 MiB of its own arenas (which leave out the host's memory) it stops for the session and components keep their structural answer with a warning that says why. It is no longer replaced after 64 programs, which raised its memory instead of lowering it (Chakra over 650 edits: 377 MiB peak against 514).
- `extract` keeps the checker's answer in its cache directory, and a rerun over unchanged files reuses it: on an app wrapping the 938 components of Chakra UI and MUI a rerun takes 0.25 s instead of 1.4 s. Before reusing it, the run asks again every question the checker asked of the disk (each file it read or looked for, each directory it listed, the tsconfig and what it extends); any different answer, a new file where it found none included, discards it whole, as does another Caliper build. `--no-cache` neither reads nor writes it, and `check`, `inspect`, a `--tsc-path` checker and the Storybook session never use it.

  A whole-project `extract` with the checker is also faster and smaller when it does ask: each property's type is asked for once per run instead of once per component, and fewer files are asked about at once. On the same app it takes about 1.4 s and 990 MiB instead of 1.7 s and 1,080 MiB; on the Chakra components alone about 1.1 s and 720 MiB instead of 1.35 s and 870 MiB. The output is the same.
- With the TypeScript checker on (`--experimental-semantic-types`, or `semanticTypes: 'on-demand'`), a component now gets the props of its own export. Before, a component the checker could not find by its name took the props of the module's default export: with `Menu.Item = Item; export default Menu`, `Item` was given `Menu`'s props and reported as resolved by the checker, and with `export { CardImpl as Card }` beside a default export, `CardImpl` was given the default export's props. Now the checker asks for the export the component really has (a renamed export, `default`, or `Menu.Item` through its parent), and a component it cannot find that way keeps the props Caliper read itself, with the reason in a `SEMANTIC_BACKEND` diagnostic. The output's shape is unchanged, and the parse cache is rebuilt once.

  For library users: `ComponentMapping` and `ComponentEntry` record how the module exports each component (`exports`, a list of `ComponentExport`), and `ComponentMapping::exported()` replaces the `exported` field. `SemanticTarget` carries the component's output `key` and its `exports` in place of `exported`, and `SemanticComponent` and `SemanticFallback` name the component by that `key` in place of `file_path` and `display_name`; the merge finds the entry by key.
- The TypeScript checker built into Caliper is now the only one it runs. The option that ran a checker binary as a separate process instead is gone, and with it the version check of that binary. Output with the built-in checker is unchanged.

  Breaking: `--tsc-path`, the config's `tscPath`, and the `tscPath` option of the native binding and the Storybook addon are removed. The CLI and the config refuse them as unknown, and the addon refuses `tscPath` by name, since left unread it would quietly run a different checker than the one it named. For library users, `caliper-docgen-semantic` loses `SemanticRequest::tsc_path`, `expected_versions` and `extra_env`, `OnDemandConfig::tsc_path`, `expected_versions` and `extra_env`, `OnDemand::process_id`, `OnDemand::recycles` with `Recycles` (the built-in checker is never replaced), and `SUPPORTED_VERSIONS`, and no longer depends on `caliper-docgen-tsc-client`, which is not released any more; `caliper-docgen-core` loses `PipelineOptions::semantic_tsc_path`.

  Action: drop `--tsc-path` and `tscPath`. The built-in checker answers without them; nothing needs to be installed.
- The experimental TypeScript checker is now built in: `--experimental-semantic-types` and `semanticTypes: 'on-demand'` use the `tsrs` checker linked into Caliper, so there is nothing to install, and a project's own `typescript` or `tsrs` is no longer looked for. It is still off by default. The CLI binary and the native binding are each about 22 MB larger, and their npm packages carry tsrs's `NOTICE`.
- With `semanticTypes: 'on-demand'`, a story whose component the TypeScript checker is already answering (for the warm-up, a fill, or another story) now waits for that answer instead of asking the checker again behind it, and the checker answers the stories you open before warm-up and fill work. `sessionWarmUp` no longer waits for the checker: it queues each component behind the stories, and the answers are kept for the stories that follow. Background work still runs: after 4 story answers in a row it gets the next turn. For library users: `WatchSession::components_in_background` asks at background priority without waiting, `SemanticProvider::request_at` takes a `SharedPriority` and a `Delivery` (with a default that calls `request`), and `OnDemand` answers by priority.
- With `semanticTypes: 'on-demand'`, the warm TypeScript checker keeps its snapshot between requests and brings it up to date with the files the session says changed (`updateSnapshot`), instead of reading the whole program again for every request. Answers are the same bytes as before. An edit nobody announced (a file the checker read changed, and neither `update_file` nor `ensure_fresh` saw it) is found before the checker answers from the old text: that answer is read again from the disk and carries a `SEMANTIC_BACKEND` warning naming the file. A checker warning that comes with an answer is now shown on every answer it applies to; only "unavailable" is still said once per session.

  For library users: `SemanticProvider::changed(SourceChange)` is how a `WatchSession` tells its checker what changed (a default that does nothing suits a provider that reads every file afresh), and `OnDemand::snapshots()` counts the snapshots answers came from, `created` from the disk or `updated` from the one before. The checker is still off by default.
- With `--experimental-semantic-types`, the checker's answer now covers every kind of type it states, not just the simple ones: tuples with optional, rest and labeled elements, enum members, `bigint` literals, `unique symbol`, template literals, overloaded and constructor signatures, `readonly` properties, and mapped, conditional and utility types as the checker resolved them. A type that recurses (including an alias of an array or tuple of itself) is marked as a reference back to itself, while `Box<Box<string>>` stays two nested objects; a callback keeps its optional parameters even when it is written through an alias, and a callback whose parameters cannot be read is marked as degraded instead of being given required ones. A type cut at a depth or size limit is marked `truncated` instead of standing in as the checker's text. A type from a dependency (an interface, or an object alias) stays a name; the TypeScript lib's utilities such as `Partial` and `Record` are expanded. A union's members come back in the order they were written. The checker is still off by default.
- With `--experimental-semantic-types` or `semanticTypes: 'on-demand'`, a prop the TypeScript checker answers for takes its `parent`, `declarations` and JSDoc tags from the checker, and the component its `composes`, instead of from Caliper's own pass. `parent` keeps its meaning: the interface that declares the prop, with the file as it is on disk, and none for a prop of a type literal; a prop picked or omitted from an interface (`Pick`, `Omit`) names that interface. `composes` lists the React types the props type is made of (`RefAttributes`, `HTMLAttributes`, also of a generic interface instantiated as `Props<string>`), no longer the types Caliper could not follow where the checker did. A union's members the checker sorted are put back in the written order in more cases (a union of string values, a type named through a namespace, an `undefined` Caliper dropped). The checker asks for descriptions in one round trip per component, and once per declaration, so a whole run is faster (938 Chakra and MUI wrappers: about 15 s to 9 s). The checker is still off by default. For library users: `SemanticProp` has `tags`, `parent` and `declarations`, `SemanticComponent` has `composes`, `None` when the checker could not tell and the structural `composes` stays, and `merge_semantic_props` takes the component's `composes` as an `Option<&[String]>`.

### Patch Changes

- `bigint` is now a type of its own in the canonical JSON: a prop typed `bigint`, or `React.Key` (`string | number | bigint`), has `{ "kind": "bigint" }` where it had a type named `bigint`, whether Caliper read the type itself or the TypeScript checker (`--experimental-semantic-types`) did. The output's `schemaVersion` is 6, so the Vite plugin and the Storybook addon need the same release as the binary, and the parse cache is rebuilt once. The RDT output and the Storybook control are unchanged: the type is still `bigint`, which Storybook has no control for. For library users: `PropType` gains the variant `BigInt`, so an exhaustive `match` on it needs a new arm.
- The checker backend no longer asks for the property list of every one of a library's condition maps. Chakra's `ConditionalValue<V>` is a mapped type over the same 130 keys for every value type `V`, 538 of them in a `Button`'s props, and each was listed (31.5 MB) only to be counted and cut. The count of the first one now stands for the rest of its snapshot when none of its properties is the project's, it has no signature and no index signature, its declaration's keys hold no type parameter (a map over `keyof T` of its enclosing type's `T` is listed each time, since two instantiations over the same keys can declare their properties in a dependency and in the project), and the count is over the budget where the later map sits; the others are still printed and cut as before. A first answer for Chakra's `Button` takes 277 ms (273 to 301) instead of 433 (418 to 484) and sends 2,975 requests instead of 3,511; the output of the whole `gate-large` run is byte-identical. The whole-program run's peak memory in the checker process is about 3% higher in the measurement, and a single component's is lower.
- A whole-project `extract` with the checker (the default) is about three to four times as fast, with the same output. On an app wrapping the 938 components of Chakra UI and MUI it takes 1.8 s instead of 6.2 s, and 1.4 s instead of 5.7 s for the 787 Chakra components alone; `react-docgen-typescript` takes 7.3 s and 4.1 s on the same files. The checker's answer for a prop that many components share (Chakra's style props) is now converted and merged once instead of once per component, the answers are read on several threads, and the built-in checker answers two programs over the same files at once. Peak memory is about 10% higher (1.1 GiB instead of 0.98 on that app; 1.5 GiB on three copies of it). The Storybook session keeps asking one program.
- The built-in TypeScript checker now answers by default (ADR 0026). `extract`, `check` and `inspect` merge its answer over the structural one, prop by prop, and wait for it. A native session and the Storybook addon ask it for each component a request names, and still show the structural props first when it is slower than `semanticWaitMs` (150 ms). `--no-checker`, or `checker: false` in `docgen.config.ts`, the native options or the addon's options, runs the structural resolver alone, as before. `watch`, `extractAll` and the Vite plugin stay structural.

  The checker costs time and memory. `extract` of an app with 938 Chakra UI and MUI components takes about 6 s and 970 MiB, against 0.1 s and 200 MiB with `--no-checker`. A session that answered every one of them peaks at about 1 GB, against 380 MiB without the checker: each answer the session keeps now shares its props with the others, where before each kept its own copy, about 6.7 MiB per Chakra component.

  Breaking: `--experimental-semantic-types`, the config's `experimentalSemanticTypes` and the `semanticTypes` option of the native binding and the Storybook addon are removed. The CLI and the config reject the old names as unknown, and the addon rejects `semanticTypes` by name. `PipelineOptions::experimental_semantic_types` is now `PipelineOptions::checker`, and it is `true` by default.

  Action: drop `--experimental-semantic-types`, `experimentalSemanticTypes: true` and `semanticTypes: 'on-demand'`, since the checker now runs without them. Replace `semanticTypes: 'off'`, or a run that relied on the old structural default, with `checker: false` or `--no-checker`.
- The TypeScript checker answers sooner, with the same output. In Storybook, the warm-up now loads the project's dependencies into the checker before the first story asks, and each answer is converted on the checker's own thread: the first answer for Chakra UI's `Button` takes about 115 ms instead of 165 ms, and asking for it again after an edit about 119 ms instead of 152 ms. The warm-up holds about 10 MiB more of the checker's memory. A whole-project `extract` gives each of its two checker programs a snapshot of its own, so they no longer wait for each other, and converts the checker's answers with about 60% fewer allocations: on 938 Chakra and MUI components it takes 1.38 s instead of 1.63 s, and 1.05 s instead of 1.19 s for the 787 Chakra components alone.
- With `--experimental-semantic-types` or `semanticTypes: 'on-demand'`, a generic component whose first type parameter declares a default is read at that default, as `<Poly />` renders it: `function Poly<E extends ElementType = 'div'>(props: PolyProps<E>)` now has a `div`'s props and `as: 'div'`, where it had two props and `as` typed by the open parameter `E`. The TypeScript checker forms the instantiation itself, from a file it holds in memory and Caliper never writes to disk. When it cannot (a default the checker prints by a name only the component's module sees, or a checker build that does not read in-memory files), the component keeps its structural props and the checker diagnostic names the instantiation and the checker's error. A type parameter with no default stays open, as before. The checker is still off by default.
- `caliper-docgen extract` ends sooner: the process is about to exit, so it no longer waits to free the checker run's memory, release its snapshot and wind down its runtime (about 35-50 ms on a large project). The output is unchanged. This is a `Teardown::OneShot` run; every other caller (Storybook, watch, the binding, `check`, `inspect`) keeps the default `Teardown::Session` and frees and releases as before.
- With `--experimental-semantic-types`, a prop typed `Omit<React.ComponentPropsWithoutRef<"a">, "href">`, or an interface that extends `Omit<React.HTMLAttributes<HTMLDivElement>, "color">`, no longer comes back cut off as `truncated`: React's DOM attribute types are kept as a family (`htmlAttributes` for the element) instead of expanded into hundreds of props, and an interface you declare is always listed in full however many fields it has, with the types it extends named beside them. `ReactNode | ((open: boolean) => ReactNode)` is `ReactNode` plus the function again, and a wide `ElementType` in a nested prop stays `ElementType`. The checker is still off by default.
- A prop typed `React.ReactElement` or `JSX.Element` is no longer reported as `ReactNode`, which also accepts strings, numbers and `null`: the checker's answer keeps it as the named type `ReactElement<…>` with its arguments, or `JSX.Element`, so Storybook shows the type the prop takes. `JSX.Element` is named through its namespace, so it is not confused with the DOM's `Element`, and in a union such as `Element | React.JSX.Element | null` each member keeps the place it was written in. Only the checker path changes; `--no-checker` still reads both as `ReactNode`. The JSON schema is unchanged.

## 0.4.0

- With the experimental TypeScript checker on, a function prop keeps the optional and rest markers its parameters are written with. antd's `Progress.format` reads `(percent?: number, successPercent?: number) => ReactNode` and `ActionButton.close` reads `(...args: any[]) => void`; the checker's answer used to lose the markers, giving `(percent: undefined | number, …)` and `(args: any[]) => void`, which changes how a call site reads.
- With the experimental TypeScript checker on, a prop whose type is a name that does not resolve (an import that cannot be found, a name declared nowhere) is no longer reported as `any`. It is `opaque` and carries `degradedBy: ["unresolvableImport"]`, so a reader can tell it from a prop written as `any`.
- With the experimental TypeScript checker on, a prop whose name starts with two underscores keeps the name the source writes. Mantine's `__size`, `__vars` and `__clearable` used to come back as `___size`, `___vars` and `___clearable` (the checker keeps such names with a third underscore), so those props appeared under a name nobody wrote.
- The experimental TypeScript checker can now run on `tsrs` (`npm i tsrs`) as well as on `typescript@beta`. Caliper finds `node_modules/tsrs/bin/tsrs` when no `typescript` 7.1 is installed, and `--tsc-path` (or `tscPath`) also takes the `@tsrs/<platform>/tsrs` binary, which used to fail with "could not determine tsc's version". Only the `tsrs` build that was checked against Caliper is accepted (`0.23.0-ts7.1.0-beta`); any other `tsrs` release is refused with the usual warning until it has been checked. On Chakra, Caliper's output was identical to the one from `typescript@7.1.0-beta`. The checker is still off by default.
- The minimum supported Rust version is now 1.99, and the crates use edition 2024. Building from source needs Rust 1.99 or newer; prebuilt binaries and npm packages are unaffected, and the output is unchanged.
- Agents reading TOON output no longer lose what they need to write a valid call. A literal union such as shadcn's `size` or `variant` now lists every value instead of ending in `...(+2)`, function props keep their parameter names (`(value: string, index?: number) => void`), a prop's `@deprecated`, `@see` and `@since` notes appear in a `tags` column, and a discriminated union names its discriminant in a `discriminant:` line. TOON is about 12% longer on antd and shadcn; unions of types past 8 members and intersections past 4 are still cut, with the count.
- Prop types now keep more of what TypeScript says about them. Tuples keep their optional and rest elements and their labels: `[string, ...number[]]` used to print as `[string, number[][]]`, and `[head: string, ...tail: number[]]` used to come out partly unreadable. A spread of a known tuple, `[string, ...Tail]`, is flattened as TypeScript does. Bigint literals (`10n`), negative number literals (`-1`), `unique symbol`, enum members (`Size.Small`, offered to Storybook as its value `"small"`) and template literal patterns (`` `${number}px` ``) are represented instead of being marked opaque. An object type with several call signatures, a `new` signature, or a call signature beside properties keeps them all, and a recursive alias such as `type Json = string | Json[]` refers back to itself by name instead of being cut off. A getter is read as a property (`get size(): number` is `readonly size: number`), not as a method.

  The JSON output moves to schema version 5. A tuple's elements are now `{ "type", "label"?, "modifier"? }` objects, the type kinds `bigintLiteral`, `uniqueSymbol`, `enumMember`, `templateLiteral`, `callable`, `recursive` and `truncated` are new, and the `templateLiteral` reason of an `opaque` type is gone. Update `caliper-docgen`, the Vite plugin and the Storybook addon together; a mismatched install stops with a message naming both versions.

## 0.3.0

- The experimental on-demand TypeScript 7.1 checker now works with any 7.1 release (beta, rc or stable) instead of only `7.1.0-beta`, replaces its `tsc` process when it grows past 768 MiB between requests, and no longer makes closing a session wait for a request in progress. For library users: `PINNED_VERSIONS` is now `SUPPORTED_VERSIONS`, and `expected_versions` entries may be a `major.minor` series such as `"7.1"`.

## 0.2.0

- Storybook can now ask TypeScript 7.1 for the exact component a story shows, so props that only the type checker can see appear in its controls (shadcn's components gain more than twice as many). It is experimental and off by default: set `semanticTypes: 'on-demand'` in the addon options and install `typescript@beta`. A story waits up to 150 ms for the checker and otherwise shows the usual props, with the checker's answer ready for the next request. Props the checker does not see stay, so `children`, `aria-*` and DOM handlers appear as `htmlAttributes` says, in both modes.

## 0.1.1

- Publish the TypeScript transport and semantic backend crates before the CLI. The CLI's runtime opt-in backend remains available in its crates.io distribution, and every local crate dependency now has a version requirement that Cargo can publish.
